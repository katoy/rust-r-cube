## 指摘（優先順）

### F1 — P2: 写真を差し替えても旧写真の 3 面を適用できる

**再現:** 実ブラウザで solved の画像 A/B を読み取ると `faces` は完成局面の 6 面、進捗は `6 / 6 面`、適用ボタンは有効になる。画像 A を別局面の `scrambled-1-view-a.png` へ差し替えた後も、画像 A 自体は更新されカードは「読込完了」になる一方、`faces` の U/R/F は完成局面のままで、進捗 `6 / 6 面` と適用可能状態が続いた。[操作スクリプト](review-evidence/011a7b9/probe-ui.mjs)と[状態記録](review-evidence/011a7b9/probe-ui.json)を参照。

**原因:** [`onImageLoaded`](../web/camera.ts#L376) は `imageA` / `imageB` とカードだけを更新し、該当ビューから以前に読み取った [`faces`](../web/camera.ts#L624) を失効させない。[`update`](../web/camera.ts#L800) は `faces` のキー数だけで適用可否を決める。新画像の輪郭検出は、旧画像の色を再読取しない。

**影響・修正案:** 利用者が撮り直した写真を見ながら、古い写真の色をキューブへ渡せる。画像の再選択を始めた時点から該当ビューの 3 面を「再読取待ち」として適用不可にし、採用が確定したら旧結果と検出ラベルを失効させて表示を更新する。A/B の片側を再選択し、再キャプチャ前は `3 / 6`、再キャプチャ後は `6 / 6` になる画面テストを追加する。読込失敗時に旧結果をどう扱うかも一貫した方針にする。

### F2 — P3: 古いプリセット要求の失敗が新しい成功表示を上書きする

**再現:** 「完成状態」の取得を保留してから「簡単（3手）」を選択し、後者の成功を確認後に前者へ HTTP 503 を返した。局面は新しいプリセットのままだが、状態表示は `✓ 簡単（3手） を読み込みました` から、古い要求の `❌ 読み込み失敗` へ変わった。[ブラウザ記録](review-evidence/011a7b9/probe-ui.json)に前後の局面・表示を保存した。

**原因:** [`initializePresets`](../web/main.ts#L875) は成功経路の [`requestId` 照合](../web/main.ts#L904)で古い応答を破棄するが、[`catch`](../web/main.ts#L971) には同じ照合がない。旧要求のネットワーク・JSON エラーは新しい要求の結果を知らずに共通の `presetStatus` を書き換える。

**影響・修正案:** ネットワーク不調時、成功した選択が失敗したように見え、利用者が再試行や再操作をしやすい。成功・失敗・操作中断のすべての表示更新に最新要求 ID の照合を適用する。A 保留 → B 成功 → A 失敗、A 保留 → B 失敗 → A 成功の逆順完了をテストする。

### F3 — P3: タイムラインの `aria-valuetext` が 1 手先の手順名を現在の手として読む

**再現:** `?alg=R+U` から得た解法は `U'`, `R'` の 2 手。1 手進めたとき、`step=1` なのにタイムラインの `aria-valuetext` は `1手目: R' (...)` となった。`R'` は次に実行する 2 手目で、画面の「次の手」表示も `R'` である。[実画面の取得値](review-evidence/011a7b9/probe-ui.json)を参照。

**原因:** [`refresh`](../web/main.ts#L133) の `currentMeta` は `cachedAnalyzedMoves[step]` で、次の手を指す。これを [`aria-valuetext`](../web/main.ts#L264) に `${step}手目` として転用している。数値 `step` は完了済みの手数を表す。

**影響・修正案:** スクリーンリーダーの利用者には再生位置と手順名が食い違って伝わる。値を「1手完了。次は2手目 R'」のように明確に分けるか、完了した手を伝えるなら `step - 1` のメタデータを使う。開始・中間・最終位置のアクセシブル名を実操作で検証する。

### F4 — P3: 構文上正しい破損マニフェストでオフライン検証が再ビルドせず停止する

**再現:** 隔離ディレクトリの `.build-manifest.json` に不完全な `{` を置くと `fresh: false` となる。しかし `null` では `Object.keys` が `TypeError`、`{"src/main.rs":null}` では `prev.hash` が `TypeError` で終了した。[再現スクリプト](review-evidence/011a7b9/probe-manifest.mjs)と[結果](review-evidence/011a7b9/probe-manifest.json)を参照。

**原因:** [`checkInputsFreshness`](../scripts/build-manifest.js#L82) の `try/catch` は JSON の構文解析だけを守る。解析後の型・エントリ構造を検査せず [`Object.keys`](../scripts/build-manifest.js#L95) と [`prev.hash`](../scripts/build-manifest.js#L117) に進む。[`ensureBuild`](../scripts/launch-offline.js#L23) は `fresh: false` の場合のみ再ビルドするため、破損を検出する前に停止する。

**影響・修正案:** 部分書込みや手動編集でマニフェストが壊れた際、用意されている自動再ビルド経路が動かない。マニフェスト全体と各値の型を検証し、不正なら `fresh: false` と理由を返す。`null`、配列、欠損エントリ、無効なハッシュを使った隔離テストを加える。
