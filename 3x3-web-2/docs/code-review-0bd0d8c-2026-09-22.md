## 2. 再現した問題

### R01 — 自分のアプリ以外の Service Worker を解除する

**箇所:** [`web/pwa.ts`](../web/pwa.ts) 19–22行。

`getRegistrations()` の全結果に対して、スコープやスクリプトの所有者を確認せず `unregister()` を呼んでいる。この分岐は `?no-sw` / `window.__DISABLE_SW__` 指定時だけでなく、自動操作でない通常の Vite 開発モードでも実行される。

**再現:** 同一オリジンの `/other-app/` に実際の SW 登録を作成し、Cube Studio を `/?no-sw` で再読み込みする。

```json
{
  "name": "unrelated_service_worker_unregistered",
  "before": ["http://127.0.0.1:5183/other-app/"],
  "after": []
}
```

**影響:** 同じホストの別パスで動くアプリの SW 登録が失われる。既存タブは当面制御下に残る場合があるが、その登録による以後のオフライン起動等が維持できなくなる。キャッシュそのものの削除や、別オリジンへの影響は、この指摘には含めない。

**原因:** `public/sw.js` のキャッシュ名は配置スコープごとに分離されているが、登録を解除する入口に同じ所有権の制約がない。

**修正方針:** 解決済みの `swUrl` と当該アプリのスコープに一致する、自分が所有する登録だけを解除する。親・子・兄弟パスや別アプリの登録を一括解除しない。

**回帰テスト:** 別スコープの実 SW を登録してから、明示的な無効化と通常開発モードの抑止をそれぞれ実行し、別登録が維持されることを確認する。既存のキャッシュ衝突テストだけでは、登録解除の範囲は検証できない。

### R02 — 再生後の現在状態が保存されない

**箇所:** [`web/main.ts`](../web/main.ts) 263–270、306–312、620–624、787–791行。

ストアの購読処理は `replace` / `undo` / `redo` / `algorithm` だけを保存する。解法の再生やジャンプは `updateAfterSeek()` で実際の状態とセンター向きを更新するが、`seek` 通知は保存しない。さらに、再生完了・解法を閉じる操作・ページ非表示時にも保存がない。

**再現手順:**

1. URL に状態指定のない画面で、手順 `R U F` を適用する。
2. 解法を求めて「最後の手順へ」を押す。表示は完成状態になる。
3. 「解法を閉じる」を押す。
4. ページを再読み込みする。

**実測:**

| 時点 | 配置 | センター向き（quarter turns） |
| --- | --- | --- |
| 適用直後 | `R U F` のスクランブル | `[1,1,1,0,0,0]` |
| 解法を閉じた後のストア・表示 | 完成状態 | `[0,0,0,0,0,0]` |
| 同時点の localStorage | `R U F` のスクランブル | `[1,1,1,0,0,0]` |
| 再読み込み後 | `R U F` のスクランブル | `[1,1,1,0,0,0]` |

**影響:** 最終的に表示されていた状態が失われる。途中まで実物のキューブを動かして再開する場合も、ブラウザと実物の配置が食い違う。保存領域のエラーや不正な局面ではなく、正常に保存可能な環境で新しいスナップショットを書いていないことが原因である。

**修正方針:** 再生中の保存を間引く設計は維持できる。ただし、一時停止・完了・解法を閉じる操作で最新状態を確定保存し、ページ離脱・非表示時にも未保存分を反映する。あるいは `seek` の保存を debounce し、これらの境界で flush する。

**回帰テスト:** 最終ステップだけでなく途中ステップで停止・閉じる・再読込を行い、state と centerTurns の両方が保存前後で一致することを確認する。速度や動きを減らす設定を途中で変更すると別経路で `persist()` が走り、問題が隠れるため、設定変更なしのケースが必要。

**過去レビューとの関係:** `acdb7f4` 向けレポートでは、毎ステップの保存を省くよう勧めている。本指摘は毎ステップの同期保存への単純な回帰を求めるものではなく、間引いた後の確定保存が欠落している点を扱う。途中状態はそれ自体で合法なキューブ状態であり、保存を全面的に禁止する理由にはならない。

### R03 — 撮影とファイル選択の世代管理が分離している

**箇所:** [`web/camera.ts`](../web/camera.ts) 355–357、858–879行。

`captureLiveFrame()` は `toBlob()` の完了を待ってから `processFile()` を呼ぶ。一方、ファイル選択は直ちに `processFile()` を呼ぶ。前者の `captureRequestId` と後者の `loadGenerationA/B` が別々に管理され、ファイル選択によって保留中の撮影が無効にならない。

**再現手順:**

1. 画像Aに対してライブ撮影を行い、JPEG の `toBlob` コールバックを保留する。
2. 同じ画像Aに対して、後から640×480の画像ファイルを選択し、読込完了を待つ。
3. 先の撮影のコールバックを完了させる。

```text
新しいファイル選択後: 読込完了 (640×480)
古い撮影処理の完了後: 読込完了 (1280×960)
```

**影響:** 後のユーザー操作で選んだ画像と頂点調整対象が、古い撮影画像に差し替わる。古い処理が最後に `processFile()` に入るため、むしろ新しいロード世代を取得して上書きに成功する。

**検証の性質:** 実 Chromium、偽カメラ、実際の画像デコードを使用した。`toBlob()` 自体は元の実装を呼び、コールバックの配送順だけを保留して競合を確定させている。通常端末での発生頻度は計測していない。

**修正方針:** 画像A/Bごとに、画像を取得する操作を開始した時点で世代を確保する。撮影、ファイル選択、ドロップが共通の世代を使い、JPEG生成・デコードの両方の完了時に確認する。古い `toBlob` が `processFile()` に入って新世代を取得する構造を避ける。

**回帰テスト:** `撮影開始 → 同じ面へのファイル入力完了 → 古い撮影完了` の順序で新しいファイルが保持されること。既存の `camera-lifecycle.spec.ts` は、画像デコード同士の競合と撮影時のビュー固定を検証しているが、JPEG生成前後をまたぐ異種入力の順序は検証していない。

### R04 — セル修正でフォーカスが失われる

**箇所:** [`web/camera.ts`](../web/camera.ts) 657–666行、[`web/camera-results-ui.ts`](../web/camera-results-ui.ts) 65–68行。

色を修正するたびに `renderResults()` が全セルを `replaceChildren()` で作り直す。操作中のボタンも削除されるが、再生成した同じセルへフォーカスを戻していない。

**再現:** 完成状態の画像Aを読み取る。F面の右上セル（`data-index="2"`）へフォーカスし、Space で色を修正してから Tab を押す。

```text
修正前: BUTTON / face=F / index=2
修正後: BODY
次のTab: BUTTON / face=U / index=0
```

**影響:** 次のセルに進むはずのキーボード操作が、毎回U面の先頭からの移動になる。連続して色を補正する利用者にとって操作位置を保てない。DOM上のARIA属性が適切でも、この動的なフォーカス消失は防げない。

**修正方針:** セルDOMを保ったまま表示を更新するか、再描画後に操作元の `face` と `index` に一致するセルへフォーカスを戻す。既存の `web/editor.ts:paint()` は同じ目的の復元を行っており、挙動を揃えられる。

**回帰テスト:** 画像認識後に Space / Enter で補正し、フォーカスが同じセルに残り、Tab が次の編集可能セルへ進むことを確認する。既存の `camera-face-and-focus.spec.ts` が確認するのはパレット選択後のフォーカスであり、結果セルの補正後ではない。

## 5. 低優先度の観察とテストの改善余地

- **履歴操作の中断処理が揃っていない。** `main.ts:557–562` の undo/redo は `stop()` / `cancelSearch()` を呼ばない。追加プローブでは undo 後も進行中のアニメーションが残ることを確認したが、完了後のストア状態は正しく復元された。恒久的な状態破損とは判定していない。通常の置換・手動回転と同じ中断手順へ揃え、探索中の undo/redo も検証する余地がある。
- **カメラのラジオグループに矢印キー操作がない。** `camera-results-ui.ts:31–50` は `role="radio"` と `aria-checked` を付けるが、キーボードハンドラやフォーカス順の制御がない。実測でも最初の色で ArrowRight を押しても選択・フォーカスが動かない。ネイティブのradio入力を用いるか、グループとしてのキー操作を実装できる。TabとSpaceでの選択は可能なので、R04とは影響を区別した。
- **CFOPの探索ノード数が出力へ反映されない。** `src/cfop.rs:check_timeout()` はノード数を数えるが、`CfopResult` に含めず、`lib.rs` のCFOP分岐も `total_nodes` を更新しない。結果の `nodes` とUIの探索ノード表示は0になる。解法そのものの誤りではないが、方式比較・性能診断に使うなら出力契約を揃える必要がある。
- **テストを増やす位置は処理境界。** パレット選択だけでなくセル修正、画像デコード同士だけでなくJPEG生成とファイル選択、キャッシュ削除だけでなく登録解除、設定保存だけでなく再生後の保存を組み合わせる。コードを実行しただけのカバレッジ増加では、これらの利用者の操作を検証できない。

## 6. 検証範囲の限界と対応順

今回のセンター補正検証は、**色が揃っている状態でのセンター向き全4,096通り**に対する全数検証である。全キューブ状態に対する全ソルバーの完全性・最短性の証明ではない。CFOPの1,000例についても、別実装との全状態照合ではない。

実機のスマートフォン、Safari/Firefox、実写画像の認識率、GPUメモリの長時間プロファイル、ネットワークとストレージを同時に故障させる全組合せ、リモートCI実行履歴は未検証。15回の生成・破棄で例外がなかったという過去のプローブだけから、メモリリークが存在しないとは結論しない。

対応は、R05で品質ゲートを復旧し、R01の別アプリへの影響を閉じ、R02・R03の状態上書き／保存境界を修正し、R04のキーボード操作を直す順が妥当。それぞれ上記の再現を回帰テストへ移し、修正対象のテストと通常の必須チェックを実施する。

再現手順・コマンド一覧は [証跡README](review-evidence/0bd0d8c/README.md) に記載した。
