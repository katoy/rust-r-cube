## 優先修正事項

### R01 — Twist/Slice枝刈りテーブルが許容的ヒューリスティックではない

**根拠:** `src/tables.rs:296–314`、使用箇所 `src/search.rs:194–199`。

`x2_cube` との右積で作る対称圧縮がTwist/Sliceの距離を保存していない。対称圧縮なしの座標グラフを全探索したところ、**1,082,565状態中43,700状態で枝刈り値が正確な距離より大きかった**。比較BFSは本番の基本遷移表を使い、圧縮・枝刈り処理とは独立に全18手を等コストで探索したもの。回転モデルまで別実装であるという意味ではない。

具体的には `R D2 R U2 L D2` の `(twist=1, slice=36)` は正確な距離6に対して枝刈り値7。逆手順 `D2 L' U2 R' D2 R'` で6手で完成するが、公開APIおよびブラウザの色のみKociemba探索は `U2 R2 L2 U2 D2 L' D2 R' U2 R L2` の11手を返した。

**影響:** 存在する探索枝を不可能と判断して除外する。Kociembaが一般に最短解を保証しないこと自体を問題にしているのではなく、枝刈り値が満たすべき下界の不変条件が破られている。今回、全状態で解が失われることまでは確認していない。Korf自身のIDA*ではなく、Korf・ThistlethwaiteのKociembaフォールバックにも影響する。

**修正方針・回帰:** 正しい対称作用と向き変換で生成し直す。圧縮前BFSに対する `heuristic <= exact_distance` を検証し、上記6手例も追加する。比較対象のFlip/Sliceは1,013,760状態すべてで正確な距離と一致した。

### R02 — カメラ起動処理のストリーム所有権が曖昧

**根拠:** `web/camera.ts:766–772,781–786,834–836`。

取得後の `video.play()` が拒否されるとストリームが残り、再試行時に `this.mediaStream` が上書きされる。また、古い起動の `play()` 完了後に実行する `stopLiveStream()` が、新しい起動のストリームを止めてしまう。

**再現:** 実ソースを制御したメディアモックで、play拒否→再試行成功→停止の順に実行。古いトラックの停止回数は0、新しいトラックは1。最初のplayだけを遅延して2回起動した場合も、古いトラックは停止されず、新しいプレビューが停止した。

**影響:** 閉じたつもりでもカメラトラックが残るプライバシー・リソース管理上の問題。通常のEsc終了テストが通ることでは除外できない。物理カメラでのランプ状態は未確認。

**修正方針・回帰:** 起動を直列化するか多重起動を無効化し、各非同期リクエストが取得したローカルなストリームを、失敗・世代不一致時に必ず解放する。古い要求から新しいストリームを停止しない。拒否、重複、各await中の終了について全トラックの終了を検証する。

### R03 — 配置スコープのキャッシュ名が衝突・前方一致する

**根拠:** `public/sw.js:40–46,82–83`。

`/nested/` のプレフィックスは `cube-studio-nested-`、`/nested/cube/` は `cube-studio-nested-cube-`。前者のactivate処理が後者を自分の旧版と判定して削除する。今回生成した `dist/sw.js` でも、`cube-studio-nested-cube-a46f7fdfac` が削除対象となった。古い固定 `v1` 名に限る問題ではない。

別の衝突として、`/a/b/c_/d/` と `/a/b/c/_d/` は、どちらもスラグ `a-b_c___d` になる。現在の置換規則ではパス境界とエスケープ文字を一意に復元できない。

**影響:** 同一オリジン上の別配置をオフラインで利用できなくする。現行の配置分離テストが網羅するパスとは異なる条件で再現。

**修正方針・回帰:** 完全なスコープURLの衝突しない識別子と明確な版境界を使用する。上記パスの組合せで、初回activateと実更新の両方において他配置のキャッシュが残ることを検証する。再現は実生成SWのactivateハンドラを実行するモックで確認した。

### R04 — クリーンCIでWASMバインディング生成より先に型検査する

**根拠:** 親リポジトリ `.github/workflows/3x3-web-2.yml:60–66`、`web/main.ts:2`、`web/solver.worker.ts:1–5`、`web/centers.ts:1`。

CIは `npm run typecheck` の後で `npm run build` を実行する。`pkg/` はGit管理外で、ビルド前には `../pkg/cube_studio` の宣言ファイルがない。

**再現:** 既存 `pkg/` は移動・削除せず、ソース・設定だけを隔離コピーして実際の型検査を実行。上記3ファイルで **TS2307 / exit 1**。`vite/client` の `?url` 宣言は、このモジュール本体の欠落を解決しない。

**修正方針・回帰:** WASM生成後に型検査するか、すでにWASM生成→型検査を内包する `npm run build` に順序を集約する。生成物なしのcheckoutで実行する。なお、現状はこれより前のRust fmt/Clippyにも失敗があり、それらを直した後もこの問題が残る。

## その他の主要な不具合

### R05 — ThistlethwaiteのG3判定が半回転群への所属を保証しない

**根拠:** `src/thistlethwaite.rs:286–302`。

テトラッド所属と偶パリティだけでは条件不足。半回転6種のBFSで到達可能なコーナー置換は96通りだが、現在の条件は288通りを受理し、192通りは到達不能だった。

**再現:** `cp=[0,1,2,4,3,7,6,5]`、他は完成状態。合法なfacelet文字列は `UUDUUUUUURRRRRRRRLFFFFFFBFBDDUDDDDDDLLLLLLLLRFBBBBBFBB`。公開APIではPhase 1/2/3をすべて0手としてPhase 4へ進み、最終的にはKociembaフォールバックになった。

**影響・修正:** 半回転では解けない局面に予算を浪費し、4段階解法としての説明も崩れる。コーナーの半回転群所属を完全に判定する残余座標・表を導入し、各Phase 3出力が実際の群に属することを検証する。

### R06 — 指定探索時間がアルゴリズム間で共通の契約になっていない

**根拠:** `src/korf.rs:69–77`、`src/thistlethwaite.rs:115–125`、`src/lib.rs:103–105`。

Korf/Thistlethwaiteは残予算がなくてもフォールバックに最低1,000msを付与する。CFOPへは時間予算を渡していない。

**再現:** 初期化済み・Superflip・予算1msで、Kociembaは約1msでタイムアウト、KorfとThistlethwaiteは約1,001ms。CFOPの `scramble(948)` は予算1msに対して131.42msだった。

**修正方針・回帰:** 共通deadlineを各段階へ伝搬し、必要ならフォールバック用の予算を先に確保する。CFOPにも期限を適用する。成功・失敗だけでなく、全方式の短予算・ゼロ予算に対する経過時間を十分な許容差付きで検証する。

### R07 — 不正なWASMセンター入力が成功に見える

**根拠:** `src/lib.rs:285–292`。

`filter_map(parse().ok())` が不正トークンを捨て、6要素残らなければ「未指定」に変える。

**再現:** `solve_with_algorithm(SOLVED, 0, true, "2,0,0,0,0,garbage", "cfop")` が成功・0手。ブラウザWASMでも確認し、Uセンター180°という指定が失われた。末尾に余分な不正トークンを足して6個の数値だけ残す入力も受理される。

**修正方針・回帰:** `None` と「指定されたが不正」を区別する。全要素の解析、個数、値域を検証して明示的にエラーにする。通常UIの入力検査だけでは、公開WASM APIの契約を保護できない。

### R08 — READMEが説明する透視射影変換を実装していない

**根拠:** `web/image-sampler.ts:132–145`、`README.md:38,264`、`docs/camera-input-spec.md:49–50`。

四隅間の双線形補間は、遠近のある写真のホモグラフィではない。

**再現:** 3行を `RRR/FFF/BBB` とした面を、四隅 `(50,50),(350,50),(250,350),(130,350)` へ独立の射影変換で描画。同じ正確な四隅を `sampleFace` に渡すと、期待 `RRRFFFBBB` に対して **`RRRRRRBBB`**。生成に用いたホモグラフィで読むと期待値に一致した。

**影響・修正:** 手動で角を正しく指定しても行単位で誤認識する。4点から射影変換を求め、退化した四角形を拒否する。現行の等角・平行四辺形フィクスチャだけでなく、独立した射影フィクスチャの全9セルを検証する。

### R09 — 誤ったセンター色を面IDとして信頼する

**根拠:** `web/camera.ts:443–455,479–481`。

検出したセンター色によって保存先の面を変えるため、画像A/Bの担当面を越えて上書きする。

**再現:** solved画像AのUセンター領域だけを黄色にして読み取ると、Aの保存先が `D,R,F` になる。通常のBを読むとDが上書きされ、最終的に `D,R,F,L,B` の5面しか残らず **5 / 6** で止まる。

**修正方針・回帰:** 規定の幾何位置を保存先にしてセンター不一致を通知するか、面配置・向きを含めて整合した姿勢推定を実装する。センターは編集不可なので、現在の補正パレットだけでは回復できない。不正・重複・未知センターでも他ビューの面を失わないテストが必要。仕様書でもAs-Isの問題として認識されており、未実装の新機能要求ではない。

### R10 — 画像デコード・フレーム符号化に世代チェックがない

**根拠:** `web/camera.ts:342–368,813–820`。

同じビューで画像1→画像2を選び、デコードを2→1の順に完了させると、表示は画像1、保持URLは画像2になる。また、Aで撮影した `toBlob` の完了前にBへ切り替えて閉じると、閉じた後に `camera-B.jpg` としてBへ取り込まれた。

**影響・修正:** 新しい入力を古い結果が上書きし、撮影先も変わる。撮影開始時にビューを固定し、セッション・ビュー別の世代番号で成功/失敗コールバックを検査する。置換、再オープン、終了で無効化する。逆順デコードと終了後の符号化完了を制御したモックで再現済み。

### R11 — タブの矢印キーがグローバル再生操作へ伝播する

### R15 — バックグラウンドのキャッシュ更新が途中終了し得る

**根拠:** `public/sw.js:104–110,143–153`。

**確認範囲・修正:** モックでレスポンス解決後も更新が未完了、waitUntil登録0件を確認。ブラウザが実際に停止するタイミングまでは再現していない。更新Promiseをイベント寿命に接続し、遅延更新中の停止・再起動を含む検証を行う。

### R18 — 解法の名称・対応範囲・理論値の説明を実装に合わせる必要がある

**根拠:** `README.md:75–139,250–259`、`src/cfop.rs:24–61`、`src/korf.rs:56–58`、`src/lib.rs:140–143,149–158,179–203`。

## 構成・保守性・性能の評価

**維持したい設計:** Rustの合法性検査と完成状態の再検証、探索Workerの分離、CubeStoreへの履歴集約、カメラ幾何・描画・結果UIの分離、内容ハッシュ付きプリキャッシュは有効。URL復元の冪等性、センターの保存/共有、ストレージ無効時の操作、WebGLフォールバックにも実際の回帰テストがある。

**改善方向:** `main.ts` と `camera.ts` の非同期処理を、状態変更前の中止・世代検査・完了後の所有権解放という一貫した規約へ寄せる。単なるファイル分割より、R02/R10/R12を防ぐ境界を明確にすることが重要。`getSolution()` の可変参照など内部APIの強化は任意であり、今回実害を再現した指摘とは区別する。

**性能上の観察:** 本番WASMは約6.26MB、Three.jsチャンクは約576KBでViteの500KB警告が出た。失敗ではなく転送・起動コストの観察値。画像サンプリングは元画像全体の読み戻しを繰り返すため、大きいスマートフォン写真について、画像データの再利用・サイズ制限をプロファイルしてから判断する。今回、実機でのメモリ上限は計測していない。

**確認できた強み:** 18回転の幾何検証、センター向き2,048通りの検証に加え、描画モデルを独立の剛体回転モデルと比較し、500四半回転・27,000ステッカー角度が一致した。これはR01の探索表の問題とは別の検証であり、片方の成功をもう片方の正しさの根拠にはしていない。
