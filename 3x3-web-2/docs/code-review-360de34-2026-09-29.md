### F4 — P2: 探索中（`solving = true`）におけるファイル読み込み（`#file.onchange`）のガード欠落による探索強制キャンセルと局面破壊

- **再現**:
  Korf などの長時間の探索を実行中（`solving = true`、キャンセルボタン表示中）、
  ファイル入力（`<input type="file" id="file">`）に対してファイル読み込みイベントが発生（あらかじめファイル選択ダイアログを開いていて後から選択完了した場合や、ドラッグ＆ドロップ経由等）した。
  競合ガードが存在するはずであるにもかかわらず、**実行中の探索が突如強制中断（`cancelSearch()`）され、読み込んだファイルの内容で盤面が勝手に上書きされた**。実測証跡 [`docs/review-evidence/360de34/probe-ui.json`](review-evidence/360de34/probe-ui.json)（`f4FileLoadRaceDuringSolve`）を参照：
  - `initialRev`: `1`
  - `stateAfterLoad`: `"UUUUUUUUURRRRRRRRRFFFFFFFFFDDDDDDDDDLLLLLLLLLBBBBBBBBB"`
  - `isSearchCancelled`: `true`
  - `stateWasReplacedWithFile`: `true`
- **原因**:
  [`web/main.ts`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/main.ts#L770-L796) の `file.onchange` では：
  ```typescript
  $<HTMLInputElement>("file").onchange = async () => {
    const file = $<HTMLInputElement>("file").files?.[0];
    if (!file) return;
    const requestId = ++fileLoadRequestId;
    const at = store.getRevision();
    try {
      if (file.size > 65536) {
        throw new Error("ファイルは64KB以内にしてください。");
      }
      const content = await file.text();
      if (requestId !== fileLoadRequestId) return;
      const parsed = validateAndParseCubeJson(content, file.size);
      validate(parsed.state);
      if (at !== store.getRevision())
        throw new Error(
          "読込中にキューブが変更されました。もう一度読み込んでください。",
        );
      replace(
        parsed.state,
        true,
        centersFromInput(parsed.state, parsed.centerTurns),
      );
  ```
  となっており、`at !== store.getRevision()` のみが検査されている。
  しかし、直前のレビュー `7fc8ac3` の F3 で指摘された通り、**探索中（`solving = true`）は探索開始時に `store.getRevision()` が進まない**。
  そのため、`at !== store.getRevision()` を素通りし、直後の `replace()` が呼ばれ、その冒頭で `cancelSearch()` が発火して探索が吹き飛ぶ。
- **先行レビュー（Claude/Codex/Copilot）の見落とし理由**:
  直前の `7fc8ac3` の F3 でプリセットボタンの非同期レースのみを修正し、**同じ非同期読み込み・置換処理であるファイル入力ハンドラ（`file.onchange`）に対する `solving` ガードの横断確認** を見落としていた。
- **影響と修正案**:
  ファイル選択操作と探索のタイミング競合により、実行中の探索が不可解に打ち切られ、盤面が破壊される。
  [`web/main.ts`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/main.ts#L771) の冒頭で `if (solving) return;` を設けるか、あるいは `if (solving || at !== store.getRevision())` による厳格なガードを配置する。

### F5 — P3: `store.restoreBaseSnapshot()` と `store.setSolution(undefined)` の重複呼び出しによる二重通知・三重レンダリング

- **再現**:
  解法が表示されている状態で、解法カードの「閉じる」（`#solution-close`）をクリックした。
  `store.subscribe` リスナーで `detail.type === "solution"` の発火回数を監視したところ、**1 回のクリックに対して `notify("solution")` が 2 回連続して発火していた**。実測証跡 [`docs/review-evidence/360de34/probe-ui.json`](review-evidence/360de34/probe-ui.json)（`f5SolutionCloseDuplicateNotify`）を参照：
  - `solutionEventCount`: `2`
  - `hasDuplicateNotification`: `true`
- **原因**:
  [`web/cube-store.ts`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/cube-store.ts#L185-L198) の `restoreBaseSnapshot()` は、内部ですでに：
  ```typescript
  restoreBaseSnapshot(): boolean {
    if (this.baseSnapshot && this.solution) {
      ...
      this.solution = undefined; // すでに未定義化
      this.baseSnapshot = undefined;
      this.future = [];
      this.revision++;
      this.notify("solution"); // 1回目の通知
      return true;
    }
    return false;
  }
  ```
  を行っている。
  それにもかかわらず、[`web/main.ts`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/main.ts#L702-L707) で：
  ```typescript
  $("solution-close").onclick = () => {
    stop();
    store.restoreBaseSnapshot();
    store.setSolution(undefined); // <-- 2回目の notify("solution") が発火
    persist();
    refresh(); // <-- 3回目の refresh() が走る
  ```
  と二重に呼び出されている。
  これにより、ストアのサブスクライバー経由で `refresh()` が 2 回実行され、さらにハンドラ末尾の明示的な `refresh()` と合わせて、1 回のクローズ操作で計 3 回の DOM 全走査・クラス更新・ARIA更新が重複実行されている。
- **先行レビュー（Claude/Codex/Copilot）の見落とし理由**:
  クラスメソッド内部の副作用（`notify` 発火）を把握せず、「安全のため念のため呼んでおく」という安易なコード追加を行ったため、副作用の重複に気付けなかった。
- **影響と修正案**:
  不要な DOM 再描画とイベント処理のオーバーヘッドが発生する。
  `if (!store.restoreBaseSnapshot()) { store.setSolution(undefined); }` とする（または F1 の方針に従い `restoreBaseSnapshot` を削除して `setSolution(undefined)` のみに一本化する）。

## 既存テストで見逃す理由

1. **既存仕様との整合性を破壊したパッチの盲信 (F1)**:
   先行レビューは「閉じるボタンでスクランブルに戻るべき」という局所的な仮説を検証することだけに熱中し、コミット前に `npm test` を全件走らせなかった（あるいは失敗ログを看過した）。その結果、リポジトリが長年維持してきた仕様（R02 永続化、シーク後の Undo/Redo）を破壊するコードが混入した。
2. **正常系とタイムアウトのみの検証 (F2)**:
   ソルバーのテストは「解けるスクランブル」と「計算打ち切りタイムアウト」のみを対象としており、意図的な不正局面（パリティ不整合、センター回転不整合）を UI から投入して `#extended` ボタンや `#solver-note` の表示を検証するテストが欠落していた。
3. **点修正と水平展開の欠如 (F3, F4)**:
   直前のレビューで修正された特定の要素（`#share-link`, `#save`, プリセットボタン）のみを単体でテストし、同じ責務・構造を持つ隣接機能（`#edit-colors`, `#file.onchange`）に対する水平展開テストを行っていなかった。
4. **ブラックボックスの戻り値のみの検証 (F5)**:
   画面上の解法カードが非表示になったことだけを確認し、ストア内部で `notify` が何回発火したか、`refresh()` が何重に実行されたかを監視するリソース・イベントメトリクステストを設けていなかった。

## 改善アクションプラン（修正方針）

- [ ] **Step 1: 解法パネルクローズ時の既存仕様回復（F1, F5 対策）**
  - `web/main.ts` の `solution-close.onclick` において、`store.restoreBaseSnapshot()` の強制呼び出しを撤回し、`store.setSolution(undefined)` のみに一本化。解法プレビュー後の局面が盤面にコミットされ、Undo で元のスクランブルに戻れる仕様を回復。
  - これにより、失敗していた Playwright 3 件（`0bd0d8c:51`, `b605038:5`, `playback-controls:129`）が直ちに完全合格（GREEN）へと復帰する。
- [ ] **Step 2: 不正局面でのタイムアウト誤表示および延長ボタン誤表示の根絶（F2 対策）**
  - `web/main.ts` の `solve()` の `catch` ブロックにおいて、エラー文字列が "探索時間の上限" または "timeout" を含む場合のみ `$("extended").hidden = false` および `$("solver-note").textContent = "探索時間の上限に達しました"` を実行し、バリデーションエラー等の場合は延長ボタンを非表示にし、適切なノートを表示する。
- [ ] **Step 3: 配色エディタ起動時のベーススクランブル局面引き渡し（F3 対策）**
  - `web/main.ts` の `edit-colors.onclick` において、`const snapshot = store.getBaseSnapshot() ?? store.getSnapshot();` を取得し、プレビュー中であれば元のスクランブル局面をエディタに渡すように修正。
- [ ] **Step 4: ファイル読み込みハンドラの非同期探索ガード設置（F4 対策）**
  - `web/main.ts` の `file.onchange` において、冒頭に `if (solving) return;` を設置し、探索中のファイル読み込みによる探索強制キャンセルと局面破壊を防止。
- [ ] **Step 5: 回帰テストの配備と全件検証**
  - `tests/code-review-360de34-regression.spec.ts` を配備し、上記 F1〜F5 の是正を永久に保証。

## 総合結論

対象コミット `360de34` は、直前の `7fc8ac3` の指摘事項に対応したパッチであったが、F2 の修正が既存の確立されたコア仕様（解法プレビュー後の盤面確定と Undo サポート、および永続化 R02）を破壊し、既存テストスイートを 3 件真っ赤（FAIL）にしていた。
