## 3. 再現・原因・修正方針

### F01 — プレビュー中Redoで課題局面を失う

**再現：** `R → U → Undo → Solve → Last → Redo → Undo`。RedoでRUに戻るが、続くUndoは完成局面へ戻り、`canUndo=false`。元のR局面（センター `[0,1,0,0,0,0]`）を履歴から復元できない。

`redo()` は現在のプレビューをhistoryに積み、`baseSnapshot`を破棄する。手動変更で使われる `commitBaseSnapshotIfPreviewing()` と同じ課題局面保全がない。ただしこのヘルパーをそのまま呼ぶと `pushHistory()` がfutureを消すため、**Redo先を保持したまま保全する設計**が必要。

**修正・回帰：** base／preview／futureの各局面とセンターを明示して履歴を再構成する。上の複合操作、途中シーク、追加Undo/Redoまで確認する。閉じる・手動変更・プレビューからUndoの既存仕様を維持する。

証拠：`probe-ui.json.redoDuringPreview`。

### F02 — 非同期モーダル起動が状態ガードを迂回

**再現：** Superflipを設定し、`editor.ts`の通信を保留。色エディタをクリックしてからKorf探索開始、通信を解放する。FSMがSolvingなのにモーダルが開く。同じ局面のApplyだけで探索がキャンセルされIdleへ戻る。

起動ハンドラはawait前にのみ `canModifyCube()` を検査し、await後は無条件にopenする。エディタのapply callbackも直接 `replace()` を呼び、FSMラッパーを通らない。カメラ起動とカメラからエディタへのawait境界にも同種の構造がある。**実証したのはエディタ経路であり、全経路を個別実証したとはしない。**

**修正・回帰：** 非同期要求の世代・状態を完了時に再検査し、モーダル内の確定操作にも共通ガードを置く。探索中のApplyを黙って成功・closeさせず、拒否を表示するか、仕様として明示した中断遷移へ統一する。遅延import→探索開始→open／Applyの順で回帰する。

証拠：`probe-ui.json.delayedEditorDuringSolve`。既存の「探索中はボタンdisabled」だけではこの順序を検出できない。

### F03 — JSONの不正センター型を黙って受理

**再現：** R局面から、`state=SOLVED`、`version=1`、`centerTurns="2,0,0,0,0,0"` のJSONを読み込む。エラーは空、盤面は完成、センターは全0になる。

パーサーは非配列を `undefined` にし、下流はこれを合法な「未指定」として自動向きへ変換する。値域・長さの検証以前に、存在する壊れた指定が消える。

**修正・回帰：** 未指定legacy入力だけを許し、存在する非配列・null・オブジェクトは明示拒否する。実際のファイル入力経路から、局面・履歴が変更されないことと通知を検査する。URLには不正centersのフォールバックという別仕様があるため、機械的に同じ拒否仕様へ変更しない。

証拠：`probe-ui.json.invalidCenterTypeAccepted`。

### F04 — 写真差し替え中に旧画像を再適用

**再現：** solved A/Bを読み取り6面を揃える。Aを再検出後、scrambled Aのロード完了を保留し、「この3面を読み取る」→「色入力へ反映」を押す。読込中の3/6が6/6へ戻り、渡される54文字は旧solved状態になる。

面結果は失効するが、旧imageA・6頂点と再読取の実行能力が残る。

**修正・回帰：** ビューごとの読込状態／画像世代でボタンと `capture()` 本体をガードし、差し替え開始時に旧ガイドを失効させる。読込完了後だけでなく、読込途中の再読取・適用・デコード失敗後を確認する。

証拠：`camera-review-probes.json`。過去 `011a7b9` の結果失効は完了後の経路では成立するが、この中間状態は未防護。

### F05 — 表示はライブ、読取は旧写真

**再現：** solved Aをアップロード・検出してライブカメラを起動し、通常の3面読取を押す。偽映像の表示画素は `[0,135,0,255]` なのに、結果は旧写真の `UUUUUUUUU / RRRRRRRRR / FFFFFFFFF`。ストリームも継続している。

ライブ描画はcanvasを変えるが、`activeImage`と頂点は静止画のまま残る。

**修正・回帰：** 静止画・起動待ち・ライブ・撮影中を相互排他的にし、ライブ中の静止画読取／輪郭編集を禁止するか、同じ表示フレームを読み取る。「ファイル→ライブ→通常読取」を確認する。既存「ライブ→ファイル」だけでは不十分。

証拠：`camera-review-probes.json`。実機映像での色認識精度の評価ではない。

### F06 — 失敗した更新が旧オフラインHTMLを破壊

**再現：** 完全なAをキャッシュする。BのHTMLは配信するがBアセットを404にし、新SWのインストールを失敗させる。オフラインで再読込すると、Aのactive SWがBのHTMLを返し、BのJSがなく起動できない。`/index.html`はA、`/`はBという分裂も確認した。

network-first navigationは、新版アセットのprecache成功とは独立に、旧active版のHTMLを上書きする。新しいcacheのinstallが失敗しても旧版への書込みは戻らない。

**修正・回帰：** 文書と資源を同じ版の一貫した集合として扱う。新版の完全な集合が確保されるまで旧オフライン文書を不変に保つ。正常更新だけでなく、欠落資源・中断更新→オフライン再起動→再更新を検査する。

証拠：`infra-browser-results.json.beforeOffline/offline`、`infra-probe-results.json.failedUpdatePoisonsOldNavigation`。実ChromiumのSWで再現。

### F07 — キャッシュ書込失敗でHTTP 200を失う

**再現：** cache miss、ネットワークはJSをHTTP 200で返す一方、Cache.putを `QuotaExceededError` にする。実fetchハンドラの戻り値は `Response.error()`、status 0。

共通catchがfetch失敗とput失敗の両方を捕捉し、取得済みの成功応答を捨てる。

**修正・回帰：** cache失敗とnetwork失敗を分離し、取得済み応答は必ず返す。キャッシュ失敗も診断可能にする。HTTP成功＋put失敗、HTTP失敗＋cacheあり／なしを検査する。

証拠：`infra-probe-results.json.quotaWriteFailure`。**実ハンドラへの障害注入であり、実端末の容量を満杯にした検証ではない。**

### F08 — SW失敗でオフライン検証が無期限待機

**再現：** 起動JSは配信し、precache専用の必須資源を404にする。ページは起動するがSWはinstallに失敗し、active workerはnull、`navigator.serviceWorker.ready`は解決しない。

launcherの `page.evaluate()` 内のready待機に期限がなく、失敗処理・ブラウザ／サーバーcleanupへ到達できない。

**修正・回帰：** registration／controller待機に明示期限を置き、redundant・失敗状態を検出する。非ゼロ終了、失敗理由、所有プロセス終了まで検査する。readyがpendingであることは実ブラウザで有界観測したが、無限時間待ち続ける実験ではない。

証拠：`infra-browser-results.json.firstInstallFailureLeavesLauncherReadyAwaitPending`。

### F09 — Superflipの24手固定ゲートは仕様と不整合

**再現：** 全体suiteで72手／期待24手以下により失敗。単独1回と反復2回でも同じ72手で失敗した。一方、プリセット一括テストでは23手も観測した。

失敗時の72手を探索なしで適用すると、色22手＋センター50手で色・センターとも完成する。50手は現在の後付け補正出力と完全一致する。通常5000ms予算では同時探索に4000msを割き、見つからなければ色探索＋補正へ進む。これは実装・プリセットが許している正常なフォールバックである。

**修正・回帰：** 通常E2Eは12エッジ反転の入力、配色完成、センター完成、フェーズ／履歴整合を検査する。短手数の性能ゲートは環境・予算・許容fallbackを定義して分離する。単に上限を72へ緩めるだけでは目的を取り違える。

証拠：`superflip-isolated.log`、`superflip-repeat.log`、`rust-superflip-fallback-output.txt`。CPU競合・ウォームアップが打切りを誘発したかは未確定。**72手を不正解やソルバーの完成検証漏れと分類しない。**

証拠：`rust-msrv-api-versions.txt`。インストール済み標準ライブラリの安定化情報を確認した。旧ツールチェーン1.80でのビルドは未実行。

### F12 — 失敗した変更でFSMとstoreが不一致

**再現：** `R → Solve → not-a-move入力 → Apply`。盤面と解法カードは保持され `hasSolution=true` だが、FSMだけPreviewingからIdleに変わる。

`runCubeMutation()` はactionより先に遷移する。下流は構文エラーをcatch、空入力をreturnするので、成功の有無を状態機械へ戻せない。

**修正・回帰：** 検証／準備とcommitを分離し、実際に盤面変更を確定した時だけFSMとstoreを同時に遷移させる。不正入力・空入力・拒否・例外・正常入力で不変条件を確認する。

証拠：`probe-ui.json.failedMutationChangesFsm`。現行UIは `canSeekSolution()` を操作ガードとして使っていないため、即座にシーク不能になるとまでは主張しない。統一したFSM契約の不整合としてP3。

### F13 — shadow RenderTargetがdisposeされない

`CubeScene.dispose()`はMeshのgeometry／material／textureを走査するが、DirectionalLightの `shadow.dispose()` を呼ばない。Threeの `LightShadow.dispose()` にはmap／mapPassの破棄処理があり、renderer.disposeは代替にならない。

**実測：** geometries 11→0、textures 9→3、1024×1024 shadow targetのdisposeイベントは0。color textureとdepth textureがあり、旧Sceneは `window.cube_scene` にも保持される。

**修正・回帰：** 所有するLightShadowを明示破棄し、Scene／window参照のライフサイクルも整理する。再生成・通常disposeとcontext lossを区別して資源破棄イベントを検査する。

証拠：`probe-scene.json`。残る3 texture全部がshadow由来とは断定しない。context lossでドライバーが回収する可能性があり、通常操作で無制限にGPUリークするとまでは主張しない。

### F14 — 撮影の符号化待ちがビュー選択を巻き戻す

**再現：** Aのライブ撮影でtoBlob配送を保留→Bタブ選択→配送解放。保存先Aは正しいが、表示がBからAへ戻る。

表示世代を撮影開始時でなくJPEGコールバック後のprocessFileで取得し、後発のB選択より新しい要求になってしまう。

**修正・回帰：** 撮影開始時の表示操作世代を符号化・デコードまで引き継ぐ。保存先と表示先を別々にassertする。既存の画像デコード遅延回帰だけでなくtoBlob待ちを含める。

証拠：`camera-review-probes.json`。

### F15 — デコード失敗通知が消える

**再現：** Aをロード後、内容 `"bad image"`・MIME `image/png` のファイルを選ぶ。未選択状態になるがエラー欄は空。

onerrorがエラー設定後にupdateを呼び、そのupdateが通知を消す。縮小画像の失敗経路にも同じ順序がある。

**修正・回帰：** 描画更新から無条件の通知クリアを分離するか、更新後にエラーを設定する。壊れた画像の面数・Apply禁止だけでなく、表示された理由をassertする。

証拠：`camera-review-probes.json`。MIME拒否とは別経路。

### F16 — 4000×1画像の縮小が無言失敗

**再現：** 旧Aロード後、実際の4000×1 PNG（188 bytes）を選ぶ。縮小高さは `round(1*1600/4000)=0`。toBlobがnullになり、そのままresolveする。旧640×480画像・ガイド・有効な読取ボタンと空エラーが残る。

**修正・回帰：** 寸法を最低1へclampするか比率を明示拒否する。現世代のnull Blobはstale結果と分け、統一失敗処理へ渡す。実ファイルから旧画像の残存・UI・通知までassertする。

証拠：`camera-review-probes.json`。このケース自体には障害注入不要。null分岐を呼ぶだけのカバレッジテストでは事後条件を保証できない。

### F17 — --freshでも配信サーバーの由来を保証しない

launcherは対象URLのHTTP 200〜399だけで既存サーバーを再利用する。実関数のプローブで無関係なHTTP 200サーバーも受理された。後続READY／offline検査で無関係ページは落ち得るが、古いCube Studioなら通る可能性があり、freshなdistを検証した証明にならない。

証拠：`infra-probe-results.json.emptyCoverageGate`、`coverage-inventory.json`。プローブはcoverage集計／閾値stageの検証であり、**npm test全体が空coverageだけで必ず成功すると主張しない**。集計に捕捉されたCSSやWASMのURLを、CSS全行やRust/WASM内部の意味的カバレッジと読み替えない。
