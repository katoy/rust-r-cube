しかし、実際のソフトウェア開発における重大な不具合や脆弱性は、「型チェックが通り、単体テストが成功している領域の狭間」に潜みます。前回の修正コミット `476486d` で施された対策を 1 行ずつ追跡し、実行時挙動・リソースライフサイクル・ブラウザ仕様・群論的数学モデルと突き合わせて検証した結果、**「修正パッチ自体が引き起こす新たな状態フリーズ」** や **「仕様書・テストでの自己申告とコード実態の乖離」** が確認されました。

### 本レビューで明らかにした決定的事実

1. **修正パッチに潜む状態フリーズ（H1）**: `web/camera.ts` に追加された画像画素数・寸法検査（`checkImagePixelCount`）は、0 ピクセルや 5000 万画素超の異常画像を正しく検知して例外を投げます。しかし、例外発生時に呼び出し元の `processFile` が `this.loading[view]` を `false` に戻さず `return` してしまうため、カード UI が「読込中…」のまま永久にフリーズし、以後の画像反映ボタンが押せなくなる致命的な状態遷移不整合が存在します。
2. **物理回転と表示の乖離（H2）**: 3D アニメーション（`web/scene.ts`）において、面の回転時にピース本体と矢印は回転層に追従しますが、Supercube のセンター向きを示す数字・矢印ラベル（`centerLabels`）は回転層にアタッチされていません。そのため、回転中はセンターラベルだけが空中に静止し、アニメーション終了時に突然向きがワープする視覚的グリッチが発生します。
3. **キャッシュストレージの無制限な肥大化（M1）**: `public/sw.js` に実装された Cache Migration は、`activate` 時に旧キャッシュ内の全資産を新キャッシュへ無条件にコピーします。旧キャッシュ自体は削除されますが、新キャッシュ内に旧バージョンのハッシュ付き JS/WASM（1 世代あたり約 6.3MB）が永続的に累積され、アプリ更新を重ねるにつれてストレージ容量（Quota）を不可逆的に圧迫・枯渇させます。
4. **カバレッジ数値至上主義コードの残存（M2）**: `tests/coverage.spec.ts` は前回の修正で `assertThrows` を導入したと主張されていますが、実際には 2600 行におよぶコードの大部分でメソッドの戻り値を一切アサートせず、単にカバレッジ計測行を通過させるためだけの空呼び出しが数百箇所温存されており、プロジェクト規約（`CLAUDE.md` §4）に違反しています。
5. **テスト名と検証内容の乖離（M3）**: `tests/coverage-advanced.spec.ts` の「すべての WASM 関数の完全テスト」は 7 個の関数をテストして合格としていますが、`src/lib.rs` で公開されている WASM API は計 11 個存在し、4 つの公開 API（`is_valid`, `is_solved`, `center_parity`, `solve_with_algorithm`）が未検証のまま脱落しています。

### H1【High・確認済み】`web/camera.ts`: 画像画素数検査例外時の `this.loading[view]` 未解除およびカード UI 永久フリーズバグ

- **該当箇所**: [`web/camera.ts:574-581`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/camera.ts#L574-L581)
- **確証度**: **確認済み**（コード追跡および状態遷移照合）
- **現象**:
  前回のレビュー指摘（M5）に対応し、先頭 64KB のヘッダー解析により 0 ピクセル画像や 5000 万画素超を遮断する `checkImagePixelCount` が追加されました。
  しかし、`processFile` 内での呼び出し順序と例外ハンドリングに重大な欠陥があります。
  ```typescript
  // web/camera.ts:574-581
  if (existingGeneration === undefined) this.beginImageLoad(view);

  try {
    await checkImagePixelCount(file);
  } catch (err) {
    this.error(err instanceof Error ? err.message : String(err));
    return; // ← ここでそのままリターンしてしまう！
  }
  ```
  Line 574 の `this.beginImageLoad(view)` で `this.loading[view] = true` が設定され、該当ビューのステータスカードには「読込中…」が表示されます。
  もしユーザーが破損画像（幅または高さが 0）や巨大画像（5000万画素超）を選択・ドロップした場合、Line 577 の `checkImagePixelCount` が例外を投げ、Line 578 の `catch` ブロックでエラーメッセージを表示してそのまま `return` します。
  このとき、**`this.imageLoadFailed(view, generation)` も `this.loading[view] = false` も呼び出されません**。
- **影響**:
  1. 画面上の画像カード（`#camera-drop-a` / `#camera-drop-b`）のステータスが「読込中…」のまま永久に解除されなくなります。
  2. カメラ入力モーダルの「色入力へ反映」ボタン（`#camera-apply`）は以下のガードを持っています：
     ```typescript
     // web/camera.ts:346-350
     if (this.loading.A || this.loading.B || Object.keys(this.faces).length !== 6) return;
     ```
     `this.loading[view]` が `true` のまま残存するため、以後に正常な画像を読み込んでも、反映ボタンが永久に反応しなくなります（UI がデッドロック状態に陥る）。
- **推奨修正案**:
  `catch` ブロック内で確実に状態をリセットし、UI を最新化してから終了します。
  ```typescript
  try {
    await checkImagePixelCount(file);
  } catch (err) {
    this.imageLoadFailed(view, generation);
    this.error(err instanceof Error ? err.message : String(err));
    return;
  }
  ```

### H2【High・確認済み】`web/scene.ts`: 回転アニメーション中における Supercube センターラベルの追従欠落と視覚的静止グリッチ

- **該当箇所**: [`web/scene.ts:480-492`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/scene.ts#L480-L492), [`:515-541`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/scene.ts#L515-L541)
- **確証度**: **確認済み**（Three.js シーングラフ構造およびアニメーション処理の追跡）
- **現象**:
  3D キューブの面回転アニメーション（`turn()`）では、回転軸に沿ったレイヤー（`turnLayer`）を作成し、回転対象となる 3D オブジェクトを `layer.attach(mesh)` してクォータニオン回転させています。
  ```typescript
  // web/scene.ts:480-492
  this.pieces
    .filter((mesh) => mesh.position.dot(axis) > 0.5)
    .forEach((mesh) => layer.attach(mesh));

  const movingArrows = (this.arrowGroup.children as THREE.Object3D[]).filter(
    (mesh) => {
      mesh.getWorldPosition(CubeScene.tempVec);
      return CubeScene.tempVec.dot(axis) > 0.5;
    },
  );
  movingArrows.forEach((mesh) => layer.attach(mesh));
  ```
  ここで、ピース（`this.pieces`）と矢印（`this.arrowGroup.children`）は正しくレイヤーに attach されています。
  しかし、Supercube（センター向き考慮モード）で表示される **センターラベル（`this.centerLabels` / 6 面分の Mesh）が一切 attach されていません**。
  `centerLabels` は `this.scene`（ルート）に直接追加されたまま放置されています。
- **影響**:
  面を回転させている最中（例: U 面を 90° 回転中）、U 面のキューブピース、ステッカー、カラー矢印は滑らかに回転しているにもかかわらず、**センターに描かれた数字・矢印ラベルだけが空中に静止したまま取り残されます**。
  そしてアニメーションが完了して `finish()` が呼ばれ、`updateCenterLabels()` が実行された瞬間、静止していたラベルが突然パッと 90° 回転後の角度にワープします。
  これは Supercube アプリケーションとして極めて不自然な視覚的破綻（Visual Discontinuity）です。
- **推奨修正案**:
  1. `turn()` 内で、回転層に属するセンターラベルも `layer.attach` の対象に含めます。
     ```typescript
     for (let f = 0; f < 6; f++) {
       const label = this.centerLabels[f];
       if (label) {
         label.getWorldPosition(CubeScene.tempVec);
         if (CubeScene.tempVec.dot(axis) > 0.5) {
           layer.attach(label);
         }
       }
     }
     ```
  2. `finish()` 内で、回転レイヤーから元のシーンへ戻し、正しい位置・向きにリセットします。

### M1【Medium・確認済み】`public/sw.js`: Cache Migration における旧資産の無制限コピーとキャッシュストレージの永続的肥大化（Cache Bloat）

- **該当箇所**: [`public/sw.js:80-109`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/public/sw.js#L80-L109)
- **確証度**: **確認済み**（Service Worker ライフサイクル仕様照合）
- **現象**:
  前回のレビュー指摘（H1: `activate` で旧キャッシュが全削除されフォールバックがデッドコード化する問題）を受け、最新コミット `476486d` で「Cache Migration」方式が導入されました。
  ```javascript
  // public/sw.js:91-109
  for (const oldKey of oldKeys) {
    try {
      const oldCache = await caches.open(oldKey);
      const requests = await oldCache.keys();
      for (const req of requests) {
        const alreadyCached = await ownCache.match(req);
        if (!alreadyCached) {
          const res = await oldCache.match(req);
          if (res && res.ok) {
            await ownCache.put(req, res); // ← 旧資産を新キャッシュへ全コピー
          }
        }
      }
    } catch {}
    await caches.delete(oldKey);
  }
  ```
  この実装により、旧キャッシュ（`oldKey`）は削除されるため一見クリーンアップされているように見えます。
  しかし、中身のハッシュ付き資産（`assets/solver.worker-[hash].js` や `pkg/cube_studio_bg.wasm`）はすべて新キャッシュ（`ownCache`）へ `put` されています。
  もしユーザーがアプリを数回〜十数回にわたって更新して利用し続けた場合、**過去のすべてのバージョンの WASM バイナリ（1 つあたり約 6.3MB）と JS ファイルが新キャッシュ内に永久に累積・蓄積され続けます**。
- **影響**:
  キャッシュストレージが世代ごとに線形増大（10 回更新で 60MB 超、20 回更新で 120MB 超）し、ブラウザの Quota（容量制限）を圧迫してモバイル環境等でキャッシュエラーを引き起こします。これはレビューガイドライン重点観点 ⑤ [F5]「副作用・リソース蓄積・リークの検査」の典型的な違反です。
- **推奨修正案**:
  旧資産のマイグレーションは「直前の 1 世代のみ」に限定するか、あるいは現在接続中のクライアント（`await self.clients.matchAll()`）が存在する場合のみ一時的に保持し、クライアントが 0 件になった時点で 2 世代以上前の古いハッシュ資産をパージする世代管理（LRU/TTL）を導入します。

## 4. 数学的・幾何学的・群論的検証（正しさの完全証明）

本レビューでは、直近で導入されたアルゴリズムの数学的妥当性を厳密に検証しました。

### 4.1 Kociemba Phase 1 における 4 面奇数センター枝刈り（`min_phase1_center_moves`）の許容性（Admissibility）の証明

`src/search.rs` に実装された枝刈り関数：
```rust
fn min_phase1_center_moves(&self) -> u8 {
    if self.target_centers.is_some() {
        ((self.current_centers[1] & 1)
            + (self.current_centers[2] & 1)
            + (self.current_centers[4] & 1)
            + (self.current_centers[5] & 1)) as u8
    } else {
        0
    }
}
```

#### 【定理】
現在の局面において、面 $R(1), F(2), L(4), B(5)$ のうち残余センター回転が奇数（1 または 3 mod 4）である面の総数を $k$ とする。
Phase 1 終了時点（G1 群への到達点）でこれら 4 面のセンター残余回転をすべて偶数（0 mod 2）にするために必要な Phase 1 の残り手数は、**最低でも $k$ 手以上**である。

#### 【証明】
1. ルービックキューブの 1 回の面回転操作 $M$ において、センターが回転するのは操作された該当の 1 面のみであり、他の 5 面のセンター角度は一切変化しない。
2. したがって、任意の 1 手によって、残余回転が奇数から偶数へと変化しうる面は最大で 1 面（その面を 90° または 270° 回転させた場合）に限られる。
3. $U(0)$ 面および $D(3)$ 面の回転は、残りの 4 面（$R, F, L, B$）のセンター角度に一切影響を与えない。
4. したがって、$k$ 個の奇数面が存在する場合、それらすべてを偶数にするためには、これら $k$ 個の各面をそれぞれ最低 1 回以上回転させる必要があり、合計手数は最低でも $k$ 手を要する。
5. 一方、Phase 2（G1 群）の許可手は $\langle U, D, R^2, L^2, F^2, B^2 \rangle$ であり、$R, F, L, B$ の回転量はすべて $180^\circ \equiv 2 \pmod 4$ である。したがって、Phase 1 終了時に奇数残余回転（$1$ または $3 \pmod 4$）を持つ面が存在する場合、Phase 2 内でそれらを $0 \pmod 4$ に解消することは群論的に不可能である。
6. よって、Phase 1 の残り探索深さが $k$ 未満である場合、いかなる展開を行っても有効な解法に到達することはできず、直ちに探索枝を刈り取ることができる（Admissible）。 $\blacksquare$

この証明により、直前コミットで導入された `min_phase1_center_moves` は数学的に最短解を逃さない安全な枝刈りであることが完全に実証されました。
