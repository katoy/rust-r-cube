### R01: WASM 初期化完了前のプリセットボタン活性化と例外ハンドリング (P2)

#### 該当コード
- `web/main.ts:153-159`
- `web/main.ts:894-1006`

```typescript
// web/main.ts:153-159
document
  .querySelectorAll<HTMLButtonElement>(
    "[data-move],#scramble,#reset,#apply-algorithm,#edit-colors,#camera-colors,#save,#load",
  )
  .forEach((b) => (b.disabled = !mainReady));
```

#### 問題の構造と影響
- ページ読み込み時、`initializePresets()` は同期的に実行され、各プリセットボタン（`#preset-buttons button`）を DOM に追加する。
- 一方、WASM の初期化は非同期関数 `start()` 内の `await init({ module_or_path: wasmUrl })` で行われ、完了後に初めて `mainReady = true` となる。
- しかし、上記セレクタに `#preset-buttons button` が含まれていないため、**WASM の初期化中やネットワーク遅延時でもプリセットボタンは常に活性化状態（enabled）** になっている。
- この状態でユーザーが「ランダム（seed=1）」等のボタンをクリックすると、`scramble(data.scramble_seed)` 実行時に WASM エクスポート関数が未初期化状態であるため例外がスローされ、即座に `❌ 読み込み失敗 (TypeError: ...)` が画面に表示される。

#### 推奨修正コード
1. `refresh()` のセレクタに `#preset-buttons button` を追加:
```typescript
document
  .querySelectorAll<HTMLButtonElement>(
    "[data-move],#scramble,#reset,#apply-algorithm,#edit-colors,#camera-colors,#save,#load,#preset-buttons button",
  )
  .forEach((b) => (b.disabled = !mainReady));
```
2. クリックハンドラ冒頭にガードを追加:
```typescript
button.onclick = async () => {
  if (!mainReady) return;
  stop();
  ...
};
```

### R02: CubeStore の Undo / Redo における過剰な WASM 依存と耐障害性 (P2)

#### 該当コード
- `web/cube-store.ts:98-122`

```typescript
// web/cube-store.ts:103, 116
undo(): boolean {
  const prev = this.history.pop();
  if (!prev) return false;
  this.future.push(this.getSnapshot());
  this.state = prev.state;
  this.centerRotations = centersFromInput(prev.state, prev.centerTurns);
  ...
}
```

#### 問題の構造と影響
- `undo()` および `redo()` 内で `centersFromInput(prev.state, prev.centerTurns)` を呼び出している。
- `centersFromInput` はユーザーの任意入力（外部 JSON や手動入力）を想定した検証関数であり、内部で `center_parity(state)`（WASM 関数）を呼び出してコーナーパリティとセンター回転偶奇の一致を検証する。
- しかし、`history` / `future` に格納されるスナップショットは、すでに検証を経てストアに登録された内部データである。内部状態の復元処理で毎回 WASM パリティ計算を同期実行するのは不要なオーバーヘッドである。
- さらに深刻な点として、WASM がまだロードされていないタイミングや、万一エラーで WASM が利用不能な状態において `undo()` を呼び出すと、`center_parity` が例外をスローしてストアの内部ポインタが壊れ、以降の操作が不能になる。

#### 推奨修正コード
スナップショットからの復元では `centerTurns`（0..=3）から直接ラジアン角度を計算する:
```typescript
const quarterTurn = Math.PI / 2;

undo(): boolean {
  const prev = this.history.pop();
  if (!prev) return false;
  this.future.push(this.getSnapshot());
  this.state = prev.state;
  this.centerRotations = prev.centerTurns.map((t) => t * quarterTurn);
  this.revision++;
  this.solution = undefined;
  this.step = 0;
  this.notify("undo");
  return true;
}
```

### R03: スーパーキューブ・センター向き解決アルゴリズムにおけるペアリング順序の最適化 (P2)

#### 該当コード
- `src/supercube.rs:131-151`

```rust
// src/supercube.rs:131-143
// Step 1: Pair up faces with odd rotations (1 or 3)
while let Some(a) = (0..6).find(|&f| cur[f] % 2 != 0) {
    let Some(b) = (0..6).find(|&f| f != a && cur[f] % 2 != 0) else {
        break; // Odd count cannot be fully paired if parity was invalid
    };
    let delta_a = if cur[a] == 1 { 1 } else { -1 };
    let delta_b = -delta_a;
    let fix = rotate_two_centers(a, delta_a, b, delta_b);
    moves.extend(fix);
    cur[a] = (cur[a] - delta_a).rem_euclid(4);
    cur[b] = (cur[b] - delta_b).rem_euclid(4);
}
```

#### 問題の構造と影響
1. **補元ペア（+1 と 3）の無視**:
   - `delta_b = -delta_a` であるため、`rotate_two_centers` は「面 a を +1、面 b を -1」回転する。
   - もし `cur[a] == 1` かつ `cur[b] == 3`（つまり -1 回転が必要）であれば、この 1 回の操作で両面とも 0（解決）になる。
   - しかし、インデックス順（U, R, F, D, L, B）で単純に取り出すと、`cur[a] == 1` と `cur[b] == 1` がペアになってしまう場合がある。この場合、`b` は `1 - (-1) = 2`（180度回転）へ遷移し、後続の Step 2 で余分な 180度回転手順（12手）が発生する。
2. **隣接面優先の欠落**:
   - 隣接面同士なら約 27 手の 1 回の手順で済むが、対面同士（U↔D, R↔L, F↔B）を取り出すと中間面を経由して 2 倍（約 54 手）の手順を消費する。
3. **具体例**:
   - `[1, 0, 1, 3, 0, 3]`（U=1, F=1, D=3, B=3）の場合、現状の実装では `(U, F)` と `(D, B)` がペアになる。どちらも同符号ペアであるため 180度回転が 2 回誘発され、合計手数が 24 手以上無駄に肥大化する。
   - `(U, D)` と `(F, B)`、あるいは `(U, B)` と `(F, D)`（隣接かつ異符号）を選べば、180度回転手順は 0 回で済む。

#### 推奨改善方針
ペア選択において以下の優先順位でペアを決定するグリーディマッチングを導入する:
1. **優先度 1**: 異符号（1 と 3）かつ隣接するペア
2. **優先度 2**: 異符号（1 と 3）の対面ペア
3. **優先度 3**: 同符号かつ隣接するペア
4. **優先度 4**: その他

### R04: SolverClient におけるフェイルセーフタイマーのバッファ不足 (P2)

#### 該当コード
- `web/solver-client.ts:75-81`

```typescript
this.timer = window.setTimeout(
  () =>
    this.fail(
      "探索時間の上限に達しました。エンジンを再起動してください。",
    ),
  budget + 1500,
);
```

#### 問題の構造と影響
- メインスレッド側で `budget + 1500` ms のタイマーを設定し、超過時に Worker を強制終了している。
- しかし、Rust 側のソルバーは `budget` ミリ秒を厳格に管理しており、探索上限到達時には自律的に `Err("探索時間の上限に達しました。")` を返却するよう設計されている。
- シングルスレッドである Web ページにおいて、メインスレッドが Three.js 描画や重い DOM 処理、ガベージコレクション（GC）を実行していると、Worker からの `postMessage` イベントハンドラが 1.5 秒以上遅れて発火することがある。
- その結果、ソルバーが正常にタイムアウト結果を返信しているにもかかわらず、メインスレッドのタイマーが先に発火して Worker を破棄（terminate）してしまい、アプリが「エンジンエラー（再試行ボタン）」の異常終了状態に陥る。

#### 推奨修正コード
クライアント側の強制キルは、スレッド自体の完全停止（無限ループやクラッシュ）を救済するためのセーフティネットであるため、タイムアウト猶予を拡大する:
```typescript
const timeoutBuffer = Math.max(5000, budget * 0.5);
this.timer = window.setTimeout(
  () =>
    this.fail(
      "探索エンジンの応答が途絶えました。エンジンを再試行してください。",
    ),
  budget + timeoutBuffer,
);
```

### R05: Camera モジュールにおける Blob URL の再撮影時リーク (P3)

#### 該当コード
- `web/camera.ts:22-23`, `web/camera.ts:904-907`

```typescript
private handleDialogClose() {
  ...
  if (this.sourceUrlA) URL.revokeObjectURL(this.sourceUrlA);
  if (this.sourceUrlB) URL.revokeObjectURL(this.sourceUrlB);
  this.sourceUrlA = undefined;
  this.sourceUrlB = undefined;
}
```

#### 問題の構造と影響
- ダイアログを閉じる際には正しく `revokeObjectURL` が呼ばれている。
- しかし、ダイアログを開いたまま同一の面（View A または View B）を「再撮影」または「別の画像ファイルを再選択」した場合、古い `sourceUrlA` / `sourceUrlB` を revoke せずに新しい URL で上書きしている箇所がある。
- モバイル端末などメモリ制約の厳しい環境で複数回の再撮影を行うと、数メガバイトの画像 Blob がブラウザ内部メモリに残留する。

#### 推奨修正コード
URL 上書き前に古い URL を解放するヘルパーメソッドを用意する:
```typescript
private setSourceUrlA(url?: string) {
  if (this.sourceUrlA) URL.revokeObjectURL(this.sourceUrlA);
  this.sourceUrlA = url;
}
```

### R06: Three.js Scene の ResizeObserver における rAF デバウンスの欠落 (P3)

#### 該当コード
- `web/scene.ts:100-110`

```typescript
this.observer = new ResizeObserver(() => {
  this.resize();
});
this.observer.observe(canvas.parentElement || canvas);
```

#### 問題の構造と影響
- ブラウザウィンドウのリサイズ中、ResizeObserver は毎秒 60 回以上のコールバックを発行し、その都度 `this.resize()` → `this.renderer.setSize()` が同期実行される。
- `setSize()` は WebGL のビューポート変更だけでなく深度バッファやカラーバッファの再確保を伴うため、GPU との同期コストが高く、リサイズ操作中に顕著なフレームレート低下（カクつき）を誘発する。

#### 推奨修正コード
`requestAnimationFrame` によるフレーム単位の統合を実施する:
```typescript
let resizeRafId = 0;
this.observer = new ResizeObserver(() => {
  cancelAnimationFrame(resizeRafId);
  resizeRafId = requestAnimationFrame(() => {
    this.resize();
  });
});
```

### R07: `getScopedStorageKey` におけるパス名サニタイズの一貫性 (P3)

#### 該当コード
- `web/main.ts:34-37`

```typescript
export function getScopedStorageKey(baseKey: string): string {
  const p = typeof window !== "undefined" ? window.location.pathname : "/";
  return p.length > 1 ? `${baseKey}:${p}` : baseKey;
}
```

#### 問題の構造と影響
- `public/sw.js` の `getScopeSlug()` では、スコープパスに含まれる記号（`-`, `_`, `.`）をエスケープしてキャッシュ名の衝突や前方一致巻き込みを厳密に防御している。
- 一方、`web/main.ts` の `getScopedStorageKey` は生の `pathname` をコロンで連結しているだけである。パス名にコロンや連続スラッシュが含まれる特殊なリバースプロキシ環境（例: `example.com/app:sub/`）で、キー空間の分離が崩れるリスクがある。
- `getScopeSlug()` の設計思想と合わせて、ストレージキーにも同一のサニタイズ・スラッグ化を適用すべきである。

### R08: CFOP ソルバーの F2L における深さ 5 全探索の冗長性 (P3)

#### 該当コード
- `src/cfop.rs:180-320`

#### 問題の構造と影響
- CFOP の F2L (First Layer コーナー + Second Layer エッジ) では、各スロットを埋めるために深さ 1..=5 の反復深化探索を行っている。
- 探索枝刈り（D面エッジ破壊の抑止等）は実装されているものの、4つのスロットそれぞれで深さ 5 まで探索すると、ワーストケースで約 25 万ノードの展開が発生し、CPU 時間を数十ミリ秒消費する。
- スピードキュービングの基本である「スロットのセットアップ＋セクシームーブ／インサート（3手〜4手）」の基本定石パターンを優先的に評価することで、探索ノード数を 90% 以上削減し、瞬時の解法導出が可能となる。
