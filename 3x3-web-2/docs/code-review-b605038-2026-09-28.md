## 指摘（優先順）

### F1 — P2: 解法プレビューシーク後（または再生完了後）の再探索により、元のスクランブル局面ではなくプレビュー途中の局面が探索対象になり、元の局面情報が失われる

- **再現**:
  12手のスクランブル局面 `B L2 D F2 R2 B2 U L2 D R2 F2 U'`（`RUDDUUULUFLR...`）で Kociemba 解法（18手）を求めた後、タイムラインまたはステップボタンで 5手目（`RLLRUDRD...`）へシークした。この状態で、解法アルゴリズムを CFOP に変更し、新しい解法を求めて「解法を探す」（`#solve`）をクリックした。
  探索完了後、得られた CFOP 解法を検査したところ、元のスクランブル局面に対する解法ではなく、**シーク途中の局面（5手目）に対する解法（132手）が生成され、解法のステップ0も5手目の局面になっていた**。元のスクランブル局面およびその解法は完全に失われた。
  さらに、解法を最後まで自動再生して完成状態（SOLVED）に達した後に「解法を探す」（画面表示は「完成状態を確認」）をクリックすると、0手解法（完成状態）で上書きされ、元のスクランブル情報が消滅する。実測証跡 [`docs/review-evidence/b605038/probe-ui.json`](review-evidence/b605038/probe-ui.json)（`f1PreviewSeekSolveRace`）を参照。
- **原因**:
  [`solve()`](../web/main.ts#L478) の冒頭で `store.setSolution(undefined)` を呼んでいる。[`CubeStore.setSolution(undefined)`](../web/cube-store.ts#L181) は [`commitBaseSnapshotIfPreviewing()`](../web/cube-store.ts#L99) を実行し、プレビュー開始前の局面 `baseSnapshot` を履歴（`history`）に push して `this.baseSnapshot = undefined` にクリアするが、**`this.state` 自体はシーク途中の局面のまま放置される**。
  直後の `solve()` では `const currentState = store.getState();` で現在の状態を取得するため、ユーザーが解こうとしていた元のスクランブル局面ではなく、**プレビューで動かした途中の局面が探索 Worker に渡されてしまう**。
- **先行レビューの見落とし理由**:
  直前のレビュー（`63bce97` の F1）は「探索開始 *後* にシーク操作を行った場合の競合レース」だけに注目し、「シーク操作を行った *後* に再探索を開始した場合に、そもそも探索対象が破壊されている」という根本的な状態機械の欠陥を完全に見落としていた。
- **影響と修正案**:
  プレビューを進めたユーザーが別のアルゴリズムを試したり再探索した際、解こうとしていた元の局面が勝手に途中の局面にすり替わり、スクランブル情報が失われる。
  `solve()` 開始時、または解法プレビュー中（`step > 0` かつ `baseSnapshot` が存在する場合）は、`this.baseSnapshot` の局面（元のスクランブル局面）にキューブ状態を復元（ロールバック）してから探索を開始するか、あるいは `CubeStore` にプレビューキャンセル・巻き戻し処理（`restoreBaseSnapshot()`）を導入する。

### F2 — P2: 探索中（`solving = true`）の Undo / Redo 操作により探索が中断されず、UI拘束とバックグラウンドでのゴースト探索が継続する

- **再現**:
  Superflip などの局面で Korf（IDA*）等の時間のかかる探索を開始した（`solving = true`、キャンセルボタン表示中、`solver-note` に「探索中 · X.X 秒 / 5 秒」と表示）。探索中に画面左下の「元に戻す（Undo）」ボタンをクリックした。
  キューブの 3D 盤面は過去の局面に戻ったが、`#cancel` ボタンは表示されたままで、タイマーも進み続け、Worker は `pending` のまま古い局面の探索を継続した。ユーザーは Undo 後の局面で新しく「解法を探す」を押すことができず、古い探索が完了またはタイムアウトするまで画面操作が拘束された。実測証跡 [`docs/review-evidence/b605038/probe-ui.json`](review-evidence/b605038/probe-ui.json)（`f2UndoDuringSolve`）を参照。
- **原因**:
  [`web/main.ts`](../web/main.ts#L165) の `refresh()` は、`#undo` / `#redo` ボタンの `disabled` 判定に `solving` を含めていない（`!mainReady || !store.canUndo()`）。また、[`undo.onclick`](../web/main.ts#L619) および `redo.onclick` は `cancelSearch()` を呼び出していない。
- **先行レビューの見落とし理由**:
  直前のレビュー（`63bce97` の F4）ではプリセットボタン押下時の `cancelSearch()` 漏れだけを修正し、同じく非同期探索中にユーザーが自由に押下できる Undo / Redo ボタンのライフサイクル制御を点検から除外していた。
- **影響と修正案**:
  局面を元に戻したにもかかわらず、画面が探索中に拘束され、ユーザーは無意味に待たされる。また不要な Worker が CPU / 電力を浪費する。
  `refresh()` で探索中は `#undo` / `#redo` を `disabled = solving` で無効化するか、またはクリック時に直ちに `cancelSearch()` を呼び出して探索 Worker を中断・リセットする（両方を適用するのが最も安全）。

### F3 — P2: 探索中（`solving = true`）に「色を入力」または「カメラで読み取り」ダイアログを開くと探索が中断されず、ダイアログ背後で解法が勝手にセット・表示更新される

- **再現**:
  探索開始直後に「色を入力」タブへ行き、「6面の色を入力」（`#edit-colors`）をクリックしてエディタダイアログを開いた。エディタダイアログが開いている最中に背後で探索が完了したところ、`editorOpen = true` のまま `hasSolution = true` になり、`has-solution` クラスが付与され、DOM の解法リストやステータスが背後で書き換わった。エディタで何も変更せずにダイアログを閉じると、自分が編集しようとしていたはずの局面の解法が勝手に画面に表示されていた。実測証跡 [`docs/review-evidence/b605038/probe-ui.json`](review-evidence/b605038/probe-ui.json)（`f3EditorDuringSolve`）を参照。
- **原因**:
  [`$("edit-colors").onclick`](../web/main.ts#L572) は `stop()` を呼ぶが `cancelSearch()` を呼ばず、[`$("camera-colors").onclick`](../web/main.ts#L580) は `stop()` も `cancelSearch()` も一切呼ばない。また、これらのボタンは `refresh()` で `disabled = solving` による無効化がされていない。
- **先行レビューの見落とし理由**:
  ダイアログ内の単体操作（カメラの画像読み込みやクアッド順序）のみを個別に検証し、「メイン画面で探索が走っている最中にモーダルダイアログを開く」という複合的なユーザー行動シナリオを検証していなかった。
- **影響と修正案**:
  モーダルダイアログ操作中に背後の状態が勝手に遷移し、利用者に認知的混乱を与える。またエディタからの適用時に古い解法との非同期競合のリスクがある。
  エディタ・カメラダイアログを開くハンドラで即座に `cancelSearch()` を呼び出すか、探索中はこれらを開けないように無効化する。

### F4 — P2: 解法自動再生中に Undo を呼ぶと `stop()` が呼ばれず、再生ループ終了後も `playing` フラグが `true` のまま孤立（ゴースト playing 状態）する

- **再現**:
  解法を表示し、自動再生ボタン（`#play`）を押して再生を開始した（`playing = true`、再生ボタンが「一時停止」表示）。再生中に `#undo` をクリックした。
  解法データは破棄されて空表示に戻ったが、再生ボタンのアイコン・ラベルは「一時停止」のままスタックした。さらに、その後再度解法を探索して再生ボタンを押しても、`playing === true` のため `stop()` 処理が誤発火して再生が開始されず、「自動再生」表示に戻るだけになった（2回クリックしないと再生が始まらない）。実測証跡 [`docs/review-evidence/b605038/probe-ui.json`](review-evidence/b605038/probe-ui.json)（`f4PlayUndoStuckState`）を参照。
- **原因**:
  [`web/main.ts`](../web/main.ts#L619) の `undo.onclick` および `redo.onclick` は `stop()` を呼んでいない。
  他の全操作（`replace`, `applyAlgorithm`, `solve`, `edit-colors`, `solution-close` 等）は冒頭で `stop()` を呼んでいるが、Undo/Redo にだけ `stop()` が欠落している。
  [`play()`](../web/main.ts#L424) 内の後処理 `if (store.getSolution() === data && run === playbackRun)` は、Undo によって `store.solution` が `undefined` にクリアされた場合、この条件が false になり `playing = false` が実行されないため、`playing` フラグが永久に `true` のまま取り残される。
- **先行レビューの見落とし理由**:
  「静止状態での Undo」と「再生ボタン単体の動作」を個別にテストしており、「再生中に Undo を押す」という非同期アニメーションと状態巻き戻しのインターバル競合を検証していなかった。
- **影響と修正案**:
  UI の状態機械が破壊され、ボタン表示と内部フラグが永久に不整合になる。
  `$("undo").onclick` および `$("redo").onclick` の冒頭で確実に `stop()` を呼び出し、再生状態・アニメーション状態を安全にリセットする。また `play()` の後処理を `finally` または無条件のリセットにする。

### F5 — P3: 解法クローズボタン（`#solution-close`）押下時のキーボードフォーカス喪失（WCAG 2.4.3 / 2.4.7 違反）

- **再現**:
  解法表示中にキーボード操作（Tab キー）で `#solution-close`（解法を閉じる）ボタンにフォーカスを当てて Enter または Space キーで実行した。
  ボタンが `hidden = true` になった直後、`document.activeElement` を検査したところ `HTMLBodyElement`（`BODY`）となり、フォーカスがページ先頭に吹き飛んでフォーカスインジケータが消失した。実測証跡 [`docs/review-evidence/b605038/probe-ui.json`](review-evidence/b605038/probe-ui.json)（`f5FocusLossAfterClose`）を参照。
- **原因**:
  [`$("solution-close").onclick`](../web/main.ts#L682) は `store.setSolution(undefined)` と `refresh()` を呼ぶが、非表示になる閉じるボタンから論理的な戻り先（例えば `#solve` ボタンなど）へフォーカスを明示的に移動させるフォーカス管理を行っていない。
- **先行レビューの見落とし理由**:
  ARIA 属性の文言（`aria-valuetext` や `aria-label`）の文字列検査に終始し、動的に要素が非表示になるインタラクティブなフォーカスフローの検査を行っていなかった。
- **影響と修正案**:
  キーボード操作者やスクリーンリーダー利用者がページ先頭（body）に投げ出され、再度 Tab キーを何十回も押して元の位置を探す必要がある（WCAG 2.1 AA 2.4.3 Focus Order 違反）。
  `solution-close` 実行時に、`$<HTMLButtonElement>("solve").focus()` など適切な論理要素へフォーカスを遷移させる。
