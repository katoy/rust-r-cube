### F1 — P2: 本番の解法は「検証済み」と表示されるが、最終検証がコンパイルから除外される

- **根拠:** [`src/lib.rs:240`](../src/lib.rs#L240) からのピース完成検証と [`src/lib.rs:254`](../src/lib.rs#L254) からのセンター完成検証は `#[cfg(debug_assertions)]` 内にある。CFOP の最終検証も [`src/cfop.rs:102`](../src/cfop.rs#L102)、Thistlethwaite の検証も [`src/thistlethwaite.rs:120`](../src/thistlethwaite.rs#L120) の条件付きコンパイルに依存する。一方、UI は [`web/main.ts:180`](../web/main.ts#L180) で常に「検証済み」と表示し、[`web/view.ts:60`](../web/view.ts#L60) でも解を表示前に検証すると説明する。
- **影響:** `npm run build` は release WASM を生成するため、配信コードではソルバーやテーブルの回帰により未完成の手順が返ってもこの検証で止まらない。テストが通ることは現在の既知局面を裏付けるが、配信時の各結果を検証した根拠にはならない。
- **提案:** アルゴリズム共通の返却直前に、手順適用後の局面と、指定時のセンター向きを無条件に確認してから `ResultData` を作る。異常時は `Err` を返す。検証コストは手数に比例するので実測し、表示文言も実装と一致させる。

### F2 — P2: 解法再生後の Undo が見かけ上の無操作になり、解法だけを消す

- **再現:** 初期状態から `R` を1手回し、解法を求め、「最後の手順へ」を押してから Undo を押す。実ブラウザで、Undo 前後の局面はともに完成状態、`canUndo` は `true → false`、解法表示は `あり → なし` となった。混ぜた局面には戻らない。
- **原因:** [`CubeStore.replace`](../web/cube-store.ts#L79) は手動操作前の完成局面を `history` に積む。解法の [`updateAfterSeek`](../web/cube-store.ts#L146) は局面を変更するが履歴は更新せず、[`canUndo`](../web/cube-store.ts#L64) は古い履歴を基にボタンを有効化する。[`undo`](../web/cube-store.ts#L98) は完成局面を取り出して現在の完成局面に設定し、解法を消す。[`web/main.ts:610`](../web/main.ts#L610) の UI からそのまま実行できる。
- **提案:** 解法再生による局面変更を履歴にどう扱うか決め、Undo の遷移先と有効状態を一致させる。少なくとも、先頭履歴が現在の局面と同じ状態で Undo を有効にしない。スクランブル → 解法最終手 → Undo/Redo の回帰テストを追加する。

### F3 — P2: JSON の 64KB 制限が読み込み前のメモリ使用量を制限していない

- **根拠:** [`web/main.ts:741`](../web/main.ts#L741) は選択ファイルを `await file.text()` で全文読み込む。その後の [`validateAndParseCubeJson`](../web/file-io.ts#L6) で初めて [`fileSize > 65536`](../web/file-io.ts#L10) を拒否する。
- **影響:** 誤って巨大な JSON ファイルを選ぶと、64KB を超えると分かっていてもブラウザが全文を文字列化する。大きなファイルでは待機、メモリ圧迫、タブ終了が起こり得る。現在のサイズ制限は構文解析を防ぐだけで、読み込みは防いでいない。
- **提案:** `file.text()` より前に `file.size` を確認する。ヘルパー側の検査は別の呼び出し元への防御として残す。大きな `File` の `text()` が呼ばれないことをテストする。

### F4 — P2: 同じ配信の `/` と `/index.html` で保存状態が分離する

- **根拠:** [`getScopedStorageKey`](../web/main.ts#L37) は末尾の `/` のみを正規化して `location.pathname` をキーに含める。ルートでは `/` が `cube-studio-v1`、`/index.html` が `cube-studio-v1:/index.html` となる。サブディレクトリでも `/nested/cube/` と `/nested/cube/index.html` は別キーになる。
- **影響:** `index.html` から直接開いて回転した後、画面上のホームリンク `./` に移ると、保存済み局面・センター向き・再生設定が復元されない。同一アプリの URL 表現だけで状態が失われたように見える。
- **提案:** 保存キーは配信ディレクトリを基準に正規化し、末尾の `/index.html` を同じスコープとして扱う。ルートとサブディレクトリの両方で URL を行き来するテストを追加する。

### F5 — P3: 共有リンクを開くたび Service Worker に HTML の別エントリが増える

- **根拠:** [`public/sw.js:103`](../public/sw.js#L103) のナビゲーション処理は、成功したすべての `request` を [`cache.put(request, clone)`](../public/sw.js#L111) で保存する。Cache API のキーにはクエリが含まれるため、異なる `?state=...` の共有リンクはそれぞれ新しい HTML エントリになる。オフライン復元側は [`ignoreSearch: true`](../public/sw.js#L121) で既存エントリを使える。
- **影響:** 多くの共有局面を開くと同じ HTML が重複し、キャッシュが無制限に増える。容量上限に達すると後続のキャッシュ更新が失敗し得る。
- **提案:** ナビゲーションの HTML はスコープ内の正規 URL 一つへ保存し、クエリごとの複製を作らない。異なる共有リンクを連続訪問した後のエントリ数を確認する。

### F6 — P3: オフライン検証スクリプトは古い `dist` を検証し得る
