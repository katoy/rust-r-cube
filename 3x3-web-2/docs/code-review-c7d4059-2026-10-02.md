### H1【High・確認済み】カメラ入力: センター色で面を付け替える処理で、ステッカーの向きを補正していない

- **箇所**: `web/camera.ts:666-703`（`capture()` 内で、センター色に応じて面を動的に割り当てる処理）
- **現象**: 面の割当先はセンター色を見て付け替えますが、9 マスの並びの向きはそのままです。センターは上書きされて正しい色になるため、展開図は正常に見えます。利用者は誤りに気づけません。
- **再現**: 3D キューブを正射影して合成画像を作り、実コードの `sampleFaceFromPixels` / `computeCenter` / `rotatePointsArray` / `buildState` と、`capture()` の割当ロジック（逐語コピー）を通しました（scratchpad `camera/sim.ts`）。
  - 画像A を (1,1,1) 軸まわりに 120° 回した持ち方（赤が上など）で撮ると、U/R/F の 3 面がすべて誤ります。U は真値 `DUUBULDBF` に対し `FBDLUBUUD`（180° 回転）、240° の場合は 90° 回転になりました。画像B も同様に、D/B または L/B が不一致になります。
  - 「🔄 枠を回転」で救済できるのは step=4 のときだけです。step 1/2/3/5 はすべて不一致でした。
  - 画像A の U センター領域を緑に塗ってセンターを誤認させると、U と F のステッカー列が丸ごと入れ替わりました。ロゴ付きの白センターや反射で、現実に起こり得ます。
- **既知性**: `docs/camera-input-spec.md` §3.2 は、センター誤判定による誤割当を TODO として認めています。ただし「認識が正しくても、持ち方次第で向きが壊れる」ことは記載されていません。
- **修正案**:
  - 仕様の To-Be どおり、マッピングを固定にします（A は U/R/F、B は D/L/B）。
  - センターが期待色と異なる場合は警告を出し、「枠を 120° 回してください」と案内します。
  - 動的割当を残す場合は、ずれたステップ数に応じて 9 マスを回転させます。

### M5【Medium・コード上確認】共有 URL のクエリが残るため、リロードのたびに作業内容が戻る

- **箇所**: `web/main.ts:937-961`、`web/url-params.ts`（`web/` 内に `history.replaceState` / `pushState` の呼び出しが 1 か所もない）
- **現象**: 起動時は、localStorage を復元した後で、`?state=` / `?alg=` の値を `store.replace(..., false)` で上書きします。URL は残り続けるので、リロードや PWA の再起動のたびに共有局面へ戻ります。`record=false` のため、それまでの局面は Undo でも戻せません。`?solver=` も、保存されている解法の選択を毎回上書きします。
- **再現**: `/?alg=R` を開く → U を回す → リロードすると、R だけ回した状態に戻ります。
- **修正案**:
  - 共有パラメータを適用した直後に、`history.replaceState(null, "", location.pathname + location.hash)` で消します。
  - その後に `persist()` を呼びます。
  - 「操作 → リロード」の E2E テストを追加します（原則 ②）。

### M6【Medium・コード上確認】タイムアウト後の「30秒で再探索」を押しても、エンジンを再起動するだけで探索しない

- **箇所**: `web/solver-client.ts:79-85, 110-116`、`web/main.ts:494-499, 545-549, 659, 964-966`
- **現象**:
  1. クライアント側でタイムアウトすると、`SolverClient.fail()` が呼ばれます。Worker を terminate し、`status("error")` を通じて `engineError = true` にします。
