### R01 — Service Worker キャッシュ残存による一括 E2E テストの失敗（P1）

**根拠:** [tests/sw-update.spec.ts](../tests/sw-update.spec.ts)、[tests/ui-interaction.spec.ts:47–112](../tests/ui-interaction.spec.ts#L47-L112)

`npm test`（Playwright）を一括実行した際、テストスイート 141 番目のテストで以下のタイムアウトエラーが発生し、全体の実行が失敗する：

```
1) [chromium] › tests/ui-interaction.spec.ts:47:3 › R11, R12 & Preset Metadata Fixes › R12: delayed preset response does not overwrite concurrent user edits
  Error: expect(locator).toContainText(expected) failed
  Locator: locator('#preset-status')
  Expected substring: "優先"
  Received string:    "✓ 完成状態 を読み込みました"
  Timeout: 10000ms
```

**原因の追究と実証:**
`tests/ui-interaction.spec.ts` 単体で実行すると成功する（3 passed / 7.8秒）。しかし一括実行すると必ず失敗する。
直前に実行される `tests/sw-update.spec.ts` が同一オリジン（`http://127.0.0.1:5173`）に登録した Service Worker と Cache Storage をクリーンアップせずに終了している。
そのため、`ui-interaction.spec.ts` が `page.route("**/cubes/solved.json", ...)` でネットワークリクエストを保留しようとしても、ブラウザの Service Worker がそれをインターセプトしてキャッシュから即座に応答（Cache Hit）を返してしまう。
結果として、テストコードが `page.keyboard.press("r")` でユーザー操作を行う前にプリセット読み込みが完了してしまい、「ユーザー操作優先」のガード処理が発火せずアサーションに失敗する。

**影響:**
CI（`.github/workflows/3x3-web-2.yml:70`）における `npx playwright test` が確実に失敗する。テスト間の状態漏洩（State Pollution）が存在し、テストスイートの信頼性を損ねている。

**修正案:**
1. `tests/ui-interaction.spec.ts`（および SW を前提としない通常テスト）の `beforeEach` において、Service Worker の登録解除とキャッシュクリアを行う：
   ```typescript
   await page.evaluate(async () => {
     const regs = await navigator.serviceWorker.getRegistrations();
     await Promise.all(regs.map((r) => r.unregister()));
     const keys = await caches.keys();
     await Promise.all(keys.map((k) => caches.delete(k)));
   });
   ```
2. `tests/sw-update.spec.ts` の `afterAll` または各 SW テストのクリーンアップ処理で、登録した SW を確実にアンレジスターする。

**問題の証明:**

### R04 — Kociemba センター同時最適化成功時に `phase_infos` が消失（P2）

**根拠:** [src/lib.rs:154–214](../src/lib.rs#L154-L214)、[docs/review-evidence/c95d097/probe.rs](../docs/review-evidence/c95d097/probe.rs)

Kociemba ソルバーで「向きも含めて揃える（スーパーキューブ）」を選択した場合のフェーズ生成ロジックに重大な不整合がある。

**現象の追究:**
1. `search_oriented` による同時最適化が**成功した場合**：
   - 探索によって色とセンター向き（6面すべて回転0）が同時に解決される。
   - `center_fixes` は空（`is_empty() == true`）となる。
   - その結果、197〜212行目のブロックがスキップされ、`phase_infos` は **要素数 0 の空ベクタ（`[]`）** のまま返される。
2. フロントエンド（`web/triggers.ts:101–120`）の挙動：
   - `phases` が空であるため、「phases 情報がない従来処理」にフォールバックする。
   - 解決手順の末尾の動きから G1 手を推定し、「Phase 1: 縮約」「Phase 2: 解決」という無関係なバッジを表示する。
   - **ユーザーには「センター向きが解かれたのかどうか」が一切表示されない。**
3. 同時最適化に**失敗して後付け補正が動いた場合**：
   - 200〜211行目により、`[色解法 (Kociemba), センター向き解決]` の 2 つのフェーズが表示される。

**影響:**

**修正案:**
同時最適化が成功した場合（`moves_opt.is_some()`）にも、明示的なフェーズ情報を付与する：

```rust
        end: moves.len(),

```

### R05 — ネイティブ環境でのエラー表示時にプロセスがクラッシュ（P2）

**根拠:** [src/lib.rs:258–268](../src/lib.rs#L258-L268)、[docs/review-evidence/c95d097/probe.rs](../docs/review-evidence/c95d097/probe.rs)

先行レビュー（81cf84d）の R03 指摘に対し、コミット `c95d097` では以下の関数が導入された：

```rust
#[inline]
fn to_js_error(err: impl std::fmt::Display) -> JsValue {
    #[cfg(target_arch = "wasm32")]
    {
        JsValue::from_str(&err.to_string())
    }
    #[cfg(not(target_arch = "wasm32"))]
    {
        let _ = err;
        JsValue::UNDEFINED
    }
}
```

**致命的な欠陥の実証:**
ネイティブ環境で `apply_moves` や `validate` を呼び出し、返ってきた `Err(js_val)` を `println!("{:?}", js_val)` や `format!("{:?}", js_val)` 等でデバッグ出力しようとすると、以下の通り即座にパニックしてプロセスが異常終了する：

```
thread 'main' panicked at wasm-bindgen-0.2.128/src/lib.rs:1249:1:
cannot call wasm-bindgen imported functions on non-wasm targets
```

**原因:**
`wasm_bindgen::JsValue` の `Debug` トレイト実装は、内部で wasm-bindgen のインポート関数を呼び出す。non-wasm ターゲットで `JsValue::UNDEFINED` のインスタンスに対してフォーマット処理を行うと、wasm-bindgen ランタイムが存在しないため即座にパニックする。
また、`let _ = err;` によりエラーメッセージが完全に破棄されるため、ネイティブ側からは失敗の理由（不正な手順文字列、色の不整合、パリティ異常など）を追跡することが一切できない。

**修正案:**
クレートのコアロジックは純粋な Rust 型（`Result<T, String>`）を返す設計とし、WASM 向けのエクスポート境界のみで `JsValue` への変換を行う：
```rust
// コアロジック (native / wasm 共通で利用可能・パニックフリー)
pub fn apply_moves_core(state: &str, moves: &str) -> Result<ResultData, String> { ... }

// WASM エクスポート境界 (wasm32 のみ、または wasm-bindgen 用)
#[wasm_bindgen]
pub fn apply_moves(state: &str, moves: &str) -> Result<String, JsValue> {
    apply_moves_core(state, moves)
        .and_then(|v| serde_json::to_string(&v).map_err(|e| e.to_string()))
        .map_err(|e| JsValue::from_str(&e))
}
```

### R06 — アニメーション再生中のプリセット読み込みが誤破棄される（P2）

**根拠:** [web/main.ts:860–885](../web/main.ts#L860-L885)、[web/cube-store.ts:146–156](../web/cube-store.ts#L146-L156)

プリセット機能には「非同期フェッチ中にユーザーが手動でキューブを回した場合、プリセットによる上書きを防ぎ手動操作を優先する」という安全ガードが備わっている：

```typescript
// web/main.ts:862
const initialRevision = store.getRevision();
// ... fetch 完了後 ...
if (store.getRevision() !== initialRevision) {
  presetStatus.textContent = `⚠️ 読み込み中にキューブが操作されたため、現在の操作を優先しました`;
  return;
}
```

**競合の発生フロー:**
1. ユーザーが解法を導出し、「再生（▶）」ボタンを押して手順のアニメーションを再生させる。
2. 再生中に、ユーザーが別のプリセット（例: 「スーパーフリップ」）のボタンをクリックする。
3. `$("edit-colors").onclick` などでは再生を止める `stop()` を呼んでいるが、**プリセットボタンの `onclick` ハンドラでは `stop()` が呼ばれていない**。
4. そのため、アニメーションタイマーが動き続け、ステップ送りによって `store.updateAfterSeek()` が呼ばれる。
5. `updateAfterSeek` は `this.revision++` をインクリメントする。
6. プリセット JSON のフェッチが完了した時点で `store.getRevision() !== initialRevision` となり、**「ユーザーが操作した」と誤認されてプリセットの読み込みが一方的に破棄される**。

**修正案:**
プリセットボタンのクリック時、最初に `stop()` を呼び出して再生タイマーを確実に停止させる：

### R07 — 無条件 `skipWaiting` と未処理例外によるオフライン耐性の脆弱性（P2）

**根拠:** [public/sw.js:60–87](../public/sw.js#L60-L87)、[web/main.ts:430–466](../web/main.ts#L430-L466)

先行レビュー（81cf84d / R01）で指摘された「SW更新時に旧キャッシュを即座に削除するため、既存タブで遅延ロード（カメラ・エディタ）が失敗する」問題に対し、コミット `c95d097` では `getEditor()` / `getCamera()` に `try-catch` が追加され、失敗時に `message("アプリの更新があります。ページを再読み込みしてください。")` を表示する修正が入った。

**未解決の課題:**
1. **未処理の例外（Unhandled Promise Rejection）**:
   `getEditor()` / `getCamera()` はエラーを catch してトーストを表示した後、再度 `throw err;` を行っている。しかし呼び出し元である `$("edit-colors").onclick` や `$("camera-colors").onclick` はこの Promise を `catch` していない。ブラウザコンソールに赤い `Unhandled Rejection: TypeError: Failed to fetch dynamically imported module` が出力される。
2. **復旧手段の欠如**:
   トーストで「再読み込みしてください」と表示されるが、確認ダイアログや「今すぐ再読み込み」ボタンが画面上に現れない。
3. **PWA ライフサイクルの本質的未解決**:
   根本的な原因は、Service Worker が `install` 時に無条件で `skipWaiting()` を呼び、`activate` 時に旧キャッシュを即時全削除している点にある。古いクライアント（タブ）が開いている間は旧キャッシュを保持するか、ユーザーの同意なしに `skipWaiting()` を実行しない標準的な PWA 更新フローへ移行する必要がある。

### R08 — `validate` 関数のセマンティクス矛盾（P3）

**根拠:** [src/lib.rs:282–286](../src/lib.rs#L282-L286)

```rust
#[wasm_bindgen]
pub fn validate(state: &str) -> Result<bool, JsValue> {
    cube::parse_state(state)
        .map(|c| c == coord::RawCube::default())
        .map_err(to_js_error)
}
```

**問題点:**
関数名 `validate`（妥当性検証）に対して、戻り値の `bool` は「合法かどうか（Valid）」ではなく**「完成状態かどうか（`c == RawCube::default()`）」**を返している。
- 合法なスクランブル状態を渡すと: `Ok(false)` が返る。
- 完成状態を渡すと: `Ok(true)` が返る。
- 不正な状態を渡すと: `Err(JsValue)` が返る。

呼び出し元の JavaScript（`editor.ts:51`, `main.ts:435`）は戻り値の `bool` を見ず、例外が飛ばないことだけを確認しているため、現在は偶然動いている。しかし「合法であるかを調べる関数」として外部から `if (validate(state))` と使われた場合、スクランブルされた合法なキューブがすべて「無効」と判定される危険な設計である。完成状態の判定は `is_solved` 等の独立した関数に分離し、`validate` は `Result<(), JsValue>` または合法性そのものの `bool` を返すべきである。

### R09 — カメラ起動ボタンの連打によるストリーム要求の競合（P3）

**根拠:** [web/camera.ts:770–804](../web/camera.ts#L770-L804)

`startLiveStream()` の実行時、`getUserMedia` の呼び出しから `await video.play()` が完了するまでの間、UI上のボタン（`#camera-live-stream`）が非活性化（`disabled`）も非表示（`hidden`）もされない。
ユーザーがボタンを素早く連打した場合、並行して複数の `getUserMedia` リクエストが発行され、カメラデバイスのアクセス競合や `NotReadableError` が誘発される。
処理開始時に即座にボタンを disabled にし、エラー時またはストリーム開始完了時に状態を更新するガードが必要である。
