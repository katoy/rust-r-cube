### 🚨 Finding 1: [P2 / 可観測性・安定性] `console_error_panic_hook` 未導入による WASM パニック時のスタックトレース消失

- **該当箇所**: [`Cargo.toml`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/Cargo.toml), [`src/lib.rs:330–334`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/src/lib.rs#L330-L334)
- **現象**:
  現在、Rust 側のパニックフックとして `console_error_panic_hook` が組み込まれていません。
  万が一、境界外アクセスや不正な入力変換などで Rust コアがパニックを起こした場合、ブラウザや Web Worker のコンソールには `RuntimeError: unreachable` という極めて不透明なエラーのみが出力され、パニックが発生したファイル名、行番号、スタックトレースが完全に失われます。
- **影響**:
  Web Worker 内部での探索中に予期せぬパニックが発生した場合、開発者ツールから原因を特定することが極めて困難になります。
- **改善案**:
  `Cargo.toml` に `console_error_panic_hook` を依存関係として追加し、`src/lib.rs` の `initialize()` 内でフックを登録します。

```toml
serde_json = "1"
wasm-bindgen = "0.2"
web-time = "1"

[features]
default = ["console_error_panic_hook"]
```


### ⚠️ Finding 2: [P2 / パフォーマンス & GC] `web/scene.ts` の `turn()` における毎ターン 108 回の `new THREE.Vector3()` 生成と GC プレッシャー

- **該当箇所**: [`web/scene.ts:474–482`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/web/scene.ts#L474-L482)
- **現象**:
  キューブの面回転アニメーション `turn(move, state, duration)` において、回転層に属する矢印メッシュ（カラー矢印54個＋暗色アウトライン54個＝計108個）を抽出するフィルタリング処理が行われています：
  ```typescript
  const movingArrows = (this.arrowGroup.children as THREE.Object3D[]).filter(
    (mesh) => {
      const pos = new THREE.Vector3(); // ← 毎ターン・メッシュごとに新規インスタンス生成
      mesh.getWorldPosition(pos);
      return pos.dot(axis) > 0.5;
    },
  );
  ```
  1回の回転操作ごとに 108 個の `THREE.Vector3` がヒープ上に確保されます。
  25手のスクランブルや 20〜40手のソリューション再生を連続して行うと、数千個もの微小オブジェクトが短時間に破棄され、ブラウザの V8 ガベージコレクタ（Scavenge）が頻発して 60fps アニメーションに微小なコマ落ち（Micro-stutter）を招くリスクがあります。
- **改善案**:
  クラスレベルで静的な作業用ベクトル `private static tempVec = new THREE.Vector3();` を保持し、それを使い回すことでアロケーションをゼロにします。

```typescript
// web/scene.ts

  private static tempVec = new THREE.Vector3();
  // ...
  async turn(move: string, state: string, duration: number) {
    // ...
    const movingArrows = (this.arrowGroup.children as THREE.Object3D[]).filter(
      (mesh) => {
        mesh.getWorldPosition(CubeScene.tempVec);
        return CubeScene.tempVec.dot(axis) > 0.5;
      },
    );
    movingArrows.forEach((mesh) => layer.attach(mesh));
    // ...
  }
}
```

### 💡 Finding 3: [P3 / パフォーマンス] ソルバー各モジュールにおけるタイムアウト判定の浮動小数点演算から整数比較への最適化

- **該当箇所**:
  - [`src/search.rs:148–154`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/src/search.rs#L148-L154)
  - [`src/cfop.rs:37–47`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/src/cfop.rs#L37-L47)
  - [`src/thistlethwaite.rs:65–77`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/src/thistlethwaite.rs#L65-L77)
  - [`src/korf.rs:35–47`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/src/korf.rs#L35-L47)
- **現象**:
  各ソルバーの `exhausted()` または `check_timeout()` メソッドにおいて、探索打ち切り時間の判定に以下の浮動小数点変換と乗算が使われています：
  ```rust
  if self.nodes & 1023 == 0 && self.start.elapsed().as_secs_f64() * 1000.0 >= self.budget_ms { ... }
  ```
  WebAssembly において浮動小数点変換命令（`f64.convert_i64_u`）や乗算は、整数の比較命令（`i64.ge_u`）に比べてクロック数が増加します。
- **改善案**:
  `budget_ms` を `u128` または `u64` の整数として保持し、`self.start.elapsed().as_millis() >= self.budget_ms as u128` による整数比較に統一します。

```rust
// src/search.rs (および cfop.rs, thistlethwaite.rs, korf.rs)
pub struct Search {
    // ...
    budget_ms: u128,
}

impl Search {
    pub fn new(budget_ms: u32) -> Self {
        Self {
            // ...
            budget_ms: budget_ms as u128,
        }
    }

    fn exhausted(&mut self) -> bool {
        self.nodes += 1;
        if self.nodes & 1023 == 0 && self.start.elapsed().as_millis() >= self.budget_ms {
            self.timed_out = true;
        }
        self.timed_out
    }
}
```

### ⚠️ Finding 5: [P3 / テスト堅牢性] `tests/coverage.spec.ts` におけるライブカメラ非同期待機の Flakiness 解消

- **該当箇所**: [`tests/coverage.spec.ts:1020–1033`](file:///Users/katoy/github/study-rust/rust-r-cube/3x3-web-2/tests/coverage.spec.ts#L1020-L1033)
- **現象**:
  カバレッジテストにおいて、ライブカメラの起動テストが以下のように実装されています：
  ```typescript
  const liveBtn = page.locator("#camera-live-stream");
  if (await liveBtn.isVisible()) {
    await liveBtn.click();
    await page.waitForTimeout(200); // ← 固定200msスリープ
    const takePhoto = page.locator("#camera-take-photo");
    if (await takePhoto.isVisible()) { // ← 200ms以内にgetUserMediaが完了しないと偽になりスキップされる
      await takePhoto.click();
      await page.waitForTimeout(100);
    }
  }
  ```
  マシン負荷やブラウザの処理速度によって 200ms 以内にストリームが初期化されない場合、`camera-take-photo` が表示される前に `if` 文を抜けてしまい、`camera.ts` の 904〜922 行目が Uncovered になります。その結果、`camera.ts` のカバレッジが要求閾値（95.0%）を割り込んで 93.90% となり、アサーション失敗を引き起こします。
- **改善案**:
  固定時間の `waitForTimeout` を廃止し、Playwright の明示的待機 `await expect(takePhoto).toBeVisible({ timeout: 5000 });` に置き換えます。

```typescript
// tests/coverage.spec.ts の改善案
const liveBtn = page.locator("#camera-live-stream");
if (await liveBtn.isVisible()) {
  await liveBtn.click();
  const takePhoto = page.locator("#camera-take-photo");
  await expect(takePhoto).toBeVisible({ timeout: 5000 });
  await takePhoto.click();
  const stopStream = page.locator("#camera-stop-stream");
  await expect(stopStream).toBeVisible({ timeout: 5000 });
  await stopStream.click();
}
```

## 5. 特筆すべき優れた設計・実装 (Architectural Highlights)

本プロジェクトには、他の一般的な実装と比較して極めて優れた工学的設計が随所に見られます：

1. **ゼロランタイム・プルーニングテーブル（バイナリ埋め込み）**:
   - `build.rs` により、Twist/Slice および Flip/Slice のプルーニングテーブル（数MB）をコンパイル時にバイナリ生成し、`include_bytes!` で埋め込み。
   - ブラウザロード時のテーブル生成待ち時間がゼロであり、即座に探索を開始可能。
2. **Supercube センター向き追跡の群論的プルーニング**:
   - Kociemba Phase 2 において R, F, L, B 面が 180° 回転しか行えない群論的制約を活かし、センター回転角が奇数（90° または 270°）残っている局面を即座に刈り取る（`min_phase2_center_moves`）。
   - これにより、探索空間を劇的に削減して 20〜24手 の最短解を高速出力。
3. **ロバストな Two-View カメラ画像認識**:
   - 単なる色抽出にとどまらず、四角形の外積による凸性検証、ホモグラフィ行列（透視射影変換）の特異点検証（`det < 1e-7`、`w <= 1e-5` の防御）、四角形のスケールに応じた動的サンプリング半径決定（`radius = edgeLen / 25`）を実装。
   - 撮影角度の歪みや照明のムラに対して極めて堅牢。
4. **Web Worker のスレッド並行性と即時キャンセル制御**:
   - 探索中に新しい操作やリセットが行われた際、`SolverClient.cancel()` が直ちに古い Worker を `terminate()` して再生成。
   - ブラウザのバックグラウンドスレッドが重い探索ループで占有されることを完全に防止。
5. **Three.js の GPU メモリリーク防止アーキテクチャ**:
   - 全54セルの矢印ジオメトリを共有インスタンス化し、マテリアルも色ごとにマップキャッシュ化。
   - `dispose()` 時にシーングラフをトラバースしてジオメトリ・マテリアル・テクスチャ・WebGLRenderer を明示的に解放し、長期利用時のメモリ枯渇を防止。
6. **厳格な Service Worker スコープ隔離**:
   - 同一オリジン下のサブディレクトリ展開（`/nested/cube/` 等）を想定し、他アプリのキャッシュや親スコープのキャッシュを誤って消去・汚染しないプリフィックス命名規則を確立。
