# コードレビュー基準および再発防止チェックリスト (Review Guidelines & Guardrails)

本ドキュメントは、`docs/code-review-b755b38-2026-09-27.md` で指摘された 6 つの設計・実装上の死角（F1〜F6）を教訓とし、今後の実装・コードレビューにおいて同様のレビュー漏れを恒久的に防ぐためのガイドラインおよびチェックリストです。

---

## 1. 6大重点レビュー観点 (The 6 Critical Guardrails)

実装時およびコードレビュー時には、以下の 6 つの観点についてコードとテストを必ず検証してください。

### ① [F1] 条件付きコンパイルと UI 表示・公開仕様の整合性
* **着眼点**: `#[cfg(debug_assertions)]` や `debug_assert!` などのデバッグ専用コードが、エラー判定・バリデーション・状態保証に関与していないか。
* **チェック項目**:
  - [ ] UI で「検証済み」「エラーチェック済み」と謳っている処理が、Release ビルド（本番 WASM）でも確実に実行されているか。
  - [ ] `debug_assertions` 内で `return Err(...)` や重要な状態変更を行っていないか。
  - [ ] テストにおいて、あえて壊れた入力・不正な手順を注入しても Release ビルドで正しく弾かれるか（フォールトインジェクション）。

### ② [F2] 複合操作シナリオと状態遷移ライフサイクル
* **着眼点**: 独立した複数の機能（「手動回転と履歴」「解法計算と手順再生プレビュー」など）が組み合わさった際に、状態不整合が起きないか。
* **チェック項目**:
  - [ ] 単機能（A 単体、B 単体）のテストだけでなく、「A → B → 再び A 操作（例: 回転 → 解法再生 → Undo）」の複合シーケンスをテストしているか。
  - [ ] `canUndo` / `canRedo` などの UI 制御フラグが、「履歴配列の長さ」だけでなく「現在の状態から実際に遷移可能か（無意味な自分自身への上書きでないか）」を評価しているか。
  - [ ] プレビュー表示（シークやアニメーション）と永続状態（コミットされた盤面）の境界が明確に設計されているか。

### ③ [F3] 処理順序と Fail-fast（リソース事前ガード）
* **着眼点**: 大規模メモリ確保や重い I/O 処理の前に、サイズ・型・権限などのガードが先行して実行されているか。
* **チェック項目**:
  - [ ] `file.text()` や `FileReader.readAsText()` などでファイル全体をメモリ展開する前に、`file.size` によるサイズ上限チェックが行われているか。
  - [ ] 重いパース・計算の前に、入力フォーマットの軽量な事前検証（マジックナンバー、ヘッダー検査等）が行われているか。
  - [ ] 巨大ファイルや異常データを実際にイベントハンドラに投入する統合テストが存在するか。

### ④ [F4] URL / パス表現の揺らぎとスコープ同一性
* **着眼点**: 同一アプリへのアクセスであっても、ブラウザの URL 表現（`/` vs `/index.html`、クエリパラメータ、末尾スラッシュ、サブディレクトリ）によって挙動や保存領域が分離しないか。
* **チェック項目**:
  - [ ] LocalStorage / SessionStorage / IndexedDB のキー生成において、`/` と `/index.html` が同一スコープとして扱われているか。
  - [ ] サブディレクトリ配信（例: `/nested/cube/` と `/nested/cube/index.html`）でも正しく同一性が保たれるか。
  - [ ] テスト環境（`localhost/`）だけでなく、URL パスバリエーションを意識した結合テストが存在するか。

### ⑤ [F5] 副作用・リソース蓄積・リークの検査
* **着眼点**: 一見正常に動作（成功レスポンス）していても、内部でキャッシュやメモリ、リスナーが無制限に肥大化していないか。
* **チェック項目**:
  - [ ] Service Worker の `cache.put` で、クエリパラメータ（`?state=...` 等）付きのリクエストを無加工でキャッシュキーにしていないか（開くたびに HTML が重複増殖しないか）。
  - [ ] Three.js などの描画系で、ジオメトリ・マテリアル・テクスチャの破棄（`dispose()`）または共有再利用が徹底されているか。
  - [ ] オフラインフォールバックが「たまたま成功している」ことの裏で、不要なリソースリークが隠蔽されていないか。

### ⑥ [F6] テスト支援スクリプト・ビルド成果物の鮮度保証
* **着眼点**: 検証・テスト用スクリプトが、古いビルド成果物（`dist` 等）を誤認して偽陽性（False Positive）の合格判定を出していないか。
* **チェック項目**:
  - [ ] 検証スクリプト（`launch-offline.js` 等）が、単なるファイル存在チェックだけでビルドをスキップしていないか。
  - [ ] ソースファイルとビルド成果物の更新日時（mtime）を比較して自動再ビルドするか、明示的な強制ビルド（`--fresh` / `--build`）がサポートされているか。
  - [ ] テスト用スクリプト自体の振る舞いが意図通りか。

## 2. テスト設計のアンチパターンと是正ルール

高カバレッジ（C0/C1 95〜100%）を維持しつつ、実効性のあるテストにするためのルールです。

| アンチパターン | 是正ルール |
| :--- | :--- |
| **カバレッジ稼ぎのモック引数**<br>関数の分岐を通すためだけに、あり得ない引数（例: `fileIo.validateAndParseCubeJson("{}", 70000)`）を直接渡して満足する。 | 関数の単体テストだけでなく、**UI イベントハンドラからの呼び出し順序**も含めた統合テストを書く。 |
| **正常系だけの全件パス**<br>正しい手順が返るケースだけをテストし、異常系ハンドラが本番ビルドで動いているか確認しない。 | **フォールトインジェクション**（意図的に不正解や異常データを注入）を行い、Release ビルドでも正しくエラーになることをテストする。 |
| **固定 URL 前提のテスト**<br>テストランナーで常に `http://localhost/` だけを訪問する。 | `/index.html` やサブディレクトリ、クエリ付き URL への遷移など、**URL パスバリエーション**をテストシナリオに含める。 |
| **ブラックボックスの戻り値のみの検証**<br>画面が正常に表示されたことだけを見て、内部キャッシュ件数やメモリの増大を見ない。 | キャッシュ API の登録件数や DOM / Three.js オブジェクト数の増減をアサートする**リソースメトリクステスト**を設ける。 |

## 3. 自動チェックコマンド

コミット前およびレビュー時には以下のコマンドでガードレールを検証してください。

```bash
# ガードレール静的検証
npm run check:guardrails

# リポジトリ全体の完全検証（ガードレール、Rust、Format、Build、Webテスト）
npm run check
```
