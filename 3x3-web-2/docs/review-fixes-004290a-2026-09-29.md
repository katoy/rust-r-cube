## 指摘事項別の対応詳細

### F1 (P2): 探索中（`solving = true`）のキーボード回転ショートカット発火による強制中断と局面破壊

- **問題:** 探索中、画面上の回転ボタンは無効化されているにもかかわらず、キーボードで `U`, `R`, `F`, `D`, `L`, `B` を押すと、`applyAlgorithm` 内の `cancelSearch()` が発火して探索 Worker が強制中断され、キューブが回転して局面が破壊されていた。
- **原因:** [`web/main.ts`](../web/main.ts) の `setupKeyboardShortcuts` 登録において、`onPlay` や `onSeek` には `if (solving) return;` が設置されていたが、`onMove` にだけガードが抜けていた。
- **修正内容:**
  - [`web/main.ts`](../web/main.ts): `setupKeyboardShortcuts` の `onMove` ハンドラ冒頭に `if (solving) return;` を追加し、探索中の不用意なキー入力を物理的に無効化。
- **検証結果:**
  - 回帰テスト `F1: Keyboard move shortcut during solve is ignored and search is not cancelled` にて、探索中に `KeyU` を押下しても探索がキャンセルされず、キューブの局面リビジョンが変化しないことを確認。

### F2 (P2): 探索タイムアウト／エラー発生時における `#solver-note` の「探索中 · X.X 秒 / 5 秒」ゾンビ表示残留

- **問題:** 探索が時間切れ（タイムアウト）またはエラーで終了した際、画面下部にエラーが表示され `#cancel` ボタンが消えているにもかかわらず、中央の `#solver-note` に「探索中 · X.X 秒 / 5 秒」と表示されたまま永久に残存していた。
- **原因:** `solve()` のインターバルタイマーが書き込んだ文字列を、`catch (error)` ブロックで上書き・リセットしていなかったため。
- **修正内容:**
  - [`web/main.ts`](../web/main.ts): `solve()` の `catch (error)` ブロックにおいて、`$("solver-note").textContent = "探索時間の上限に達しました";` を明示的に設定し、エラー発生時のステータスを即座に正常化。
- **検証結果:**
  - 回帰テスト `F2: Solver note is properly updated and does not retain zombie status on error` にて、エラー時に「探索中」の文字列が消え、「探索時間の上限に達しました」に正確に更新されることを確認。

### F3 (P2): 解法プレビューシーク中に「共有リンク」（`#share-link`）を押すと、スクランブル局面ではなくプレビュー途中の局面が共有される

- **問題:** 解法を最後まで再生（または途中のステップへシーク）した状態で「共有リンク」をクリックすると、解こうとしていた元のスクランブル局面ではなく、完成状態（`UUUUUUUUURRRRRRRRR...`）の URL がクリップボードにコピーされていた。
- **原因:** `share-link.onclick` が常に現在の動的盤面（`store.getState()`）を参照しており、プレビュー開始前のスナップショット（`store.baseSnapshot`）を参照していなかったため。
- **修正内容:**
  - [`web/cube-store.ts`](../web/cube-store.ts): `getBaseSnapshot(): CubeSnapshot | undefined` メソッドを追加。
  - [`web/main.ts`](../web/main.ts): `share-link.onclick` において、`const snapshot = store.getBaseSnapshot() ?? store.getSnapshot();` を参照し、プレビュー中は元のスクランブル局面およびセンター向きを優先して URL を構築するように改修。
- **検証結果:**
  - 回帰テスト `F3: Share link during preview copies scramble state instead of preview step state` にて、解法最終手までシークした状態でも、共有リンクに元のスクランブル局面が正確に含まれることを確認。

### F4 (P3): `solve()` 冒頭における `restoreBaseSnapshot()` と `setSolution(undefined)` の二重呼び出しによる重複通知

- **問題:** `solve()` の冒頭で `store.restoreBaseSnapshot()` と `store.setSolution(undefined)` を順に呼んでいたため、同一ターン内で `solution` イベントが 2 回連続で同期発火し、高コストな `refresh()` が重複実行されていた。
- **原因:** `restoreBaseSnapshot()` が成功した場合（すでに `solution = undefined` がセットされ `notify("solution")` が呼ばれている場合）でも、直後に無条件で `setSolution(undefined)` を呼んでいたため。
- **修正内容:**
  - [`web/main.ts`](../web/main.ts): `if (!store.restoreBaseSnapshot()) { store.setSolution(undefined); }` と条件分岐にし、不要な重複通知を根絶。
  - [`web/cube-store.ts`](../web/cube-store.ts): `restoreBaseSnapshot()` 内で `this.future = [];` を明示的にリセットし、巻き戻し後のやり直し履歴の整合性を強化。
- **検証結果:**
  - 回帰テスト `F4: solve() deduplicates restoreBaseSnapshot and setSolution notifications` にて、`solution` イベントの通知回数が正確に 1 回のみであることを確認。

### F5 (P3): 探索中（`solving = true`）における `#share-link` ボタンの無効化漏れ

- **問題:** 探索中、`#scramble`, `#reset`, `#save`, `#load` 等の全操作ボタンが無効化される中、フッターの `#share-link` ボタンだけが有効なまま残っていた。
- **原因:** `refresh()` の無効化対象セレクタに `#share-link` が含まれていなかったため。
- **修正内容:**
  - [`web/main.ts`](../web/main.ts): `refresh()` のセレクタに `#share-link` を追加。
- **検証結果:**
  - 回帰テスト `F5: Share link button is properly disabled during solve` にて、探索中に `#share-link` ボタンが確実に `disabled = true` になることを確認。
