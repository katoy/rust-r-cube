## 指摘事項別の対応詳細

### F1 (P2): 写真を差し替えても旧写真の 3 面を適用できる

- **問題:** 画像 A・B の片側を読み取って 6 面キャプチャ後（進捗 6 / 6 面、適用ボタン有効）、画像 A を別局面の画像に差し替えた際、画像オブジェクトやカードステータスは更新されるものの、以前に読み取った `faces`（U/R/F）が破棄されず、古い写真の色をキューブへ適用できていた。
- **原因:** [`web/camera.ts`](../web/camera.ts) の `onImageLoaded` は新画像のセットとカード表示更新のみを行い、以前の読取結果 `faces` を失効させていなかった。
- **修正内容:**
  - [`web/camera.ts`](../web/camera.ts): ビュー単位で以前の面データと検出ラベルをクリアする `clearViewResults(view: "A" | "B")` を新設。
  - `processFile` の開始時（利用者が新画像の選択・ドロップ・撮影を開始した時点）に `this.clearViewResults(view)` を呼び出し、該当ビューの面を直ちに「再読取待ち」として失効させ、進捗表示を 3/6 面へ減らし適用ボタンを無効化。
  - `onImageLoaded` 内でも確実に `clearViewResults(view)` を呼び、新画像の採用確定時に旧結果が残らないように保護。
  - 画像読み込み失敗時（`rawImage.onerror` / `resizedImage.onerror`）も該当ビューの画像オブジェクトおよび旧面データを破棄し、「未選択・再読取待ち」として一貫した状態を維持。
- **検証結果:**
  - 新規回帰テスト [`tests/code-review-011a7b9-regression.spec.ts`](../tests/code-review-011a7b9-regression.spec.ts) にて、6 面読取後に画像 A を差し替えると即座に 3/6 面・適用不可になり、再キャプチャによってのみ 6/6 面・適用可能になること、および読込失敗時も適用不可が維持されることを確認。

### F2 (P3): 古いプリセット要求の失敗が新しい成功表示を上書きする

- **問題:** プリセット選択時、先行したリクエスト（例: HTTP 503 で失敗したリクエスト）の応答が遅れて完了した際、後から選択されて成功したプリセット表示を `❌ 読み込み失敗` で上書きしていた。
- **原因:** [`web/main.ts`](../web/main.ts) の `initializePresets` で、成功パスには `requestId !== presetRequestId` の照合チェックがあったが、`catch (error)` ブロックには同照合が存在しなかった。
- **修正内容:**
  - [`web/main.ts`](../web/main.ts): `catch (error)` ブロックの先頭に `if (requestId !== presetRequestId) return;` を追加。
  - 後から別の要求が発行されていた場合、遅延して届いた古い要求のエラー表示を破棄し、最新要求の表示を保護。
- **検証結果:**
  - 新規回帰テストにて「A 保留 → B 成功 → A 失敗」および「A 保留 → B 失敗 → A 成功」の両逆順完了ケースを検証し、常に最新の要求結果が維持されることを確認。

### F3 (P3): タイムラインの `aria-valuetext` が 1 手先の手順名を現在の手として読む

- **問題:** 再生タイムラインで `step=1`（1手完了）のとき、`aria-valuetext` が `1手目: R'` と読み上げられていた。`R'` は次に実行する 2 手目であり、完了済みの手数と次に実行する手順名が混同されていた。
- **原因:** [`web/main.ts`](../web/main.ts) の `refresh` において、`cachedAnalyzedMoves[step]`（次の手情報）を `${step}手目: ...` としてそのまま転用していた。
- **修正内容:**
  - [`web/main.ts`](../web/main.ts): タイムラインの `aria-valuetext` を、現在の完了手数と次に実行する手番・手順名を明確に分離した表現に刷新。
    - 開始位置（`step === 0`）: `開始状態。次は1手目 ${nextMeta.move} (${nextMeta.phaseLabel})`
    - 中間位置（`0 < step < max`）: `${step}手完了。次は${step + 1}手目 ${nextMeta.move} (${nextMeta.phaseLabel})`
    - 最終位置（`step === max`）: `完成 (${max}手)`
- **検証結果:**
  - 新規回帰テストにて、開始位置・中間位置・最終位置でスクリーンリーダー向けアクセシブル属性が正確に切り替わることを実操作で確認。

### F4 (P3): 構文上正しい破損マニフェストでオフライン検証が再ビルドせず停止する

- **問題:** `.build-manifest.json` の内容が `null` や配列、またはエントリが `null` などの破損 JSON だった場合、`checkInputsFreshness` が `TypeError` をスローしてプロセスが停止し、`ensureBuild` による自動再ビルド経路へ進めなかった。
- **原因:** [`scripts/build-manifest.js`](../scripts/build-manifest.js) の `checkInputsFreshness` で、`JSON.parse` の構文エラーのみを捕捉し、解析結果のオブジェクト型や各エントリの `{ hash: string }` 構造を検証していなかった。
- **修正内容:**
  - [`scripts/build-manifest.js`](../scripts/build-manifest.js): `savedManifest` がオブジェクトでない、`null`、配列である場合、または各エントリが非オブジェクト・`hash` 文字列プロパティを欠いている場合に、例外を投げずに `{ fresh: false, reason: "ビルドマニフェストが破損しています" }` を返す安全ガードを追加。
- **検証結果:**
  - `null`、配列、数値、文字列、`null` エントリ、欠損エントリ、型不正ハッシュの全破損ケースで例外なく `fresh: false` が返ることを確認。
