## 指摘事項別の対応詳細

### F1 (P2): 解法プレビュー中の手動操作で、プレビュー開始前の局面を失う

- **問題:** 実画面で `R` を回し、解法を求めて「最後の手順へ」で完成状態に進んだ後、`U` を手動回転して Undo すると、完成状態に戻った時点で Undo が無効になり、プレビュー開始前の局面（`R`）へ戻れなくなっていた。
- **原因:** [`cube-store.ts`](../web/cube-store.ts) の `applyAlgorithmResult` および `replace` が、プレビュー開始前のスナップショット `baseSnapshot` を履歴に積むことなく破棄（`this.baseSnapshot = undefined`）していたため。
- **修正内容:**
  - [`web/cube-store.ts`](../web/cube-store.ts): `commitBaseSnapshotIfPreviewing()` ヘルパーを導入。
  - `applyAlgorithmResult`（`record = true` 時）、`replace`（`record = true` 時）、`setSolution` の各遷移処理において、`baseSnapshot` が存在し現在局面と異なる場合は、まず `baseSnapshot` を `history` に積んだ上で、現在局面から新局面への履歴保存を行うように改修。
  - これにより、`baseSnapshot → プレビュー局面 → 新局面` という一貫した方針で履歴が保持され、手動回転後の Undo×2 で解法前局面に復元可能となり、リセット後の Undo でも解法前局面に復元可能となった。
- **追加テスト:**
  - [`tests/code-review-125f8c8-regression.spec.ts`](../tests/code-review-125f8c8-regression.spec.ts):
    - `F1-1: R → 解法最終手 → U手動回転 → Undo×2 で最初の R 局面に復元できる`
    - `F1-2: R → 解法最終手 → リセット → Undo で解法前の R 局面に復元できる`

### F2 (P3): 同じアプリの別名URLで効果音設定が分離する

- **問題:** `/` で効果音をオフにしても、同一オリジンの `/index.html` にアクセスすると効果音がオンに戻ってしまい、保存キーが分離していた（サブディレクトリ `/nested/cube/` と `/nested/cube/index.html` でも同様）。
- **原因:** [`sound.ts`](../web/sound.ts) が `window.location.pathname` を直接キーに結合しており、[`main.ts`](../web/main.ts) の `getScopedStorageKey` の正規化処理（`/index.html` の除去や末尾スラッシュの統一）と食い違っていたため。
- **修正内容:**
  - [`web/storage-key.ts`](../web/storage-key.ts): 共通のパス正規化ストレージキー生成関数 `getScopedStorageKey` を切り出し作成。
  - [`web/main.ts`](../web/main.ts): `web/storage-key.ts` から `getScopedStorageKey` をインポート・再エクスポートして既存コード・テストとの互換性を維持。
  - [`web/sound.ts`](../web/sound.ts): `getScopedStorageKey("cube_studio_sound_enabled")` を使用するように改修。
- **追加テスト:**
  - [`tests/code-review-125f8c8-regression.spec.ts`](../tests/code-review-125f8c8-regression.spec.ts):
    - `F2: 効果音設定のストレージキーが別名URL (index.html 有無) で同一に集約される`（`/` と `/index.html`、および `/nested/cube/` と `/nested/cube/index.html` の同一性検証）

### F3 (P3): 遅れて読み込まれたカメラ画像が利用者のビュー選択を戻す

- **問題:** カメラ画面で画像Aのデコード保留中に利用者がビューBへ切り替えた際、画像Aの読み込みが完了した瞬間に表示ビューが無条件にAへ引き戻されてしまっていた。
- **原因:** [`web/camera.ts`](../web/camera.ts) の `processFile` において、画像デコード完了時に無条件で `this.currentView = view` が実行されていたため。
- **修正内容:**
  - [`web/camera.ts`](../web/camera.ts): ビュー操作の単調増加シーケンス番号 `viewActionSequence` および最新アクティブシーケンス `latestViewActivationSeq` を導入。
  - 利用者による明示的なビュー切り替え（`switchView`）時に最新シーケンスを更新。
  - ファイル読み込み開始（`processFile`）時に要求シーケンス番号 `requestSeq` を採番。
  - `onImageLoaded` ヘルパーにより、画像自体は指定ビュー（AまたはB）へ確実に保存しつつ、表示ビューの切り替えは `requestSeq >= this.latestViewActivationSeq` の場合のみ実行するように制御。
- **追加テスト:**
  - [`tests/code-review-125f8c8-regression.spec.ts`](../tests/code-review-125f8c8-regression.spec.ts):
    - `F3: 画像Aのデコード遅延中にビューBを選択した場合、Aの完了で表示が戻されない`
    - `F3-reverse: 画像Aと画像Bを順に読み込み開始し、Bが先に完了してAが遅れて完了した場合、Bの表示が維持される`

### F4 (P3): 公開ファイルの削除後も古い `dist` を最新と判定する

- **問題:** `public/` の一時アセットを削除した後に `node scripts/launch-offline.js --headless` を実行しても、現存するファイルの更新時刻のみを比較していたため削除が検知されず、古い20ファイルのアセットキャッシュを含む `dist` を「最新」と判定して再ビルドが行われなかった。
- **原因:** `ensureBuild` が現存するファイルの最新 mtime のみを参照し、過去のビルド入力ファイル一覧の情報を保持していなかったため。
- **修正内容:**
  - [`scripts/build-manifest.js`](../scripts/build-manifest.js): ビルド入力ファイル（`src`, `web`, `public`, 設定ファイル群）の一覧・サイズ・内容ハッシュを記録・検証するマニフェストユーティリティを新規作成。
  - [`scripts/generate-sw-precache.js`](../scripts/generate-sw-precache.js): `.build-manifest.json` を Service Worker プリキャッシュ対象から除外しつつ、ビルド完了時に最新入力マニフェストを `dist/.build-manifest.json` に書き出すよう改修。
  - [`scripts/launch-offline.js`](../scripts/launch-offline.js): `checkInputsFreshness` により、マニフェストと比較してファイルの削除・新規追加・内容変更を漏れなく検知し、削除時にも確実に再ビルドをトリガーするよう改修。
- **追加テスト:**
  - [`tests/code-review-125f8c8-regression.spec.ts`](../tests/code-review-125f8c8-regression.spec.ts):
    - `F4: launch-offline.js のビルドマニフェストがファイルの追加と削除を検知する`
  - 運用プローブ（一時ファイル追加 → 20アセット検知ビルド → 一時ファイル削除 → 削除検知再ビルドで19アセット復帰）の自動検証をパス。
