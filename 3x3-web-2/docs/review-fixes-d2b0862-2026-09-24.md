## 2. 各指摘事項の修正詳細

### Finding 1: WASM パニック時のスタックトレース出力 (`console_error_panic_hook`)

- **背景**:
  WebAssembly 環境（ブラウザ）で Rust コードが万一パニック（panic）を起こした場合、標準状態ではブラウザコンソールに `RuntimeError: unreachable` という極めて抽象的なエラーしか表示されず、発生したソースコードのファイル名・行番号・コールスタックが隠蔽され、障害調査が困難となる問題があった。
- **対処**:
  1. `Cargo.toml` に `console_error_panic_hook = { version = "0.1", optional = true }` を追加し、`default = ["console_error_panic_hook"]` に設定。バイナリサイズを最小化したい組み込み用途等では `--no-default-features` で除外可能な柔軟性を保持。
  2. `src/lib.rs` の `initialize()` 関数内で、`#[cfg(feature = "console_error_panic_hook")] console_error_panic_hook::set_once();` を呼び出し。
- **結果**:
  ブラウザコンソールから Rust 側の詳細なパニックメッセージおよびスタックトレースが取得可能となり、フロントエンド・WASM 境界の可観測性とデバッグ効率が大幅に向上。

### Finding 2: `web/scene.ts` の `turn()` における `Vector3` 再利用

- **背景**:
  キューブの面回転アニメーション `turn(move, state, duration)` において、回転層に属する矢印メッシュ（カラー矢印54個＋暗色アウトライン54個＝計108個）を抽出するフィルタリング処理で、メッシュごとに `new THREE.Vector3()` を都度生成していた。
  20〜40手の再生や連続スクランブルによって数千個の微小インスタンスが短時間で破棄され、ブラウザ V8 の Scavenge GC が頻発して 60fps レンダリングに微小なコマ落ち（Micro-stutter）を招く恐れがあった。
- **対処**:
  `CubeScene` クラスに静的プロパティ `private static tempVec = new THREE.Vector3();` を定義。`getWorldPosition()` の書き込み先として共有再利用する実装へ変更。
- **差分**:
  ```typescript
  // web/scene.ts
  export class CubeScene {
    private static tempVec = new THREE.Vector3();
    // ...
    async turn(move: string, state: string, duration: number) {
      // ...
      const movingArrows = (this.arrowGroup.children as THREE.Object3D[]).filter(
        (mesh) => {
          mesh.getWorldPosition(CubeScene.tempVec);
          return CubeScene.tempVec.dot(axis) > 0.5;
        },
      );
      movingArrows.forEach((mesh) => layer.attach(mesh));
      // ...
    }
  }
  ```
- **結果**:
  毎ターンのヒープ確保が 108 回から 0 回になり、GC プレッシャーが解消。

### Finding 3: ソルバー各モジュールのタイムアウト判定を整数比較へ最適化

- **背景**:
  `src/search.rs`, `src/cfop.rs`, `src/thistlethwaite.rs`, `src/korf.rs` の各探索ルーチンにおいて、探索タイムアウト判定に `self.start.elapsed().as_secs_f64() * 1000.0 >= self.budget_ms` という浮動小数点変換および乗算が使用されていた。
  WebAssembly において `f64.convert_i64_u` や `f64.mul` は整数比較命令 `i64.ge_u` よりサイクル数が多く、ホットループ内での実行オーバーヘッドが生じていた。
- **対処**:
  1. `budget_ms` を `u128` 型として保持する設計へ変更。
  2. タイムアウト判定式を `self.start.elapsed().as_millis() >= self.budget_ms` に統一。浮動小数点演算を完全に排除。
  3. 各ソルバーの単体テスト内でタイムアウトを検証していたテストコード（`budget_ms: 0.0` 等）も `u128`（`0`）に整合。
- **結果**:
  Rust 側の全 138 件のテストがパスし、WASM バイナリレベルで比較命令が整数演算へと最適化された。

### Finding 4: `tests/coverage.spec.ts` におけるライブカメラ非同期待機の安定化

- **背景**:
  カバレッジテストにおいて、ライブカメラの起動から撮影・停止に至る検証で `await page.waitForTimeout(200)` による固定スリープが行われていた。
  マシンの CPU 負荷やブラウザ側のメディアストリーム初期化速度によって 200ms 以内にボタンが表示されない場合、条件分岐がスキップされて `camera.ts` のカバレッジが 93.90% に下落し、95.0% 閾値アサーションが失敗する Flakiness があった。
- **対処**:
  固定スリープを廃止し、Playwright の Web-First Assertion である `await expect(takePhoto).toBeVisible({ timeout: 5000 });` を用いて要素の出現を確実に待機。
  また `captureLiveFrame()` の仕様（撮影成功時に内部で自動的にストリームが停止される）に適合させ、撮影成功パスと、撮影前の手動ストリーム停止パスの両方を網羅する堅牢なシナリオに再設計。
- **結果**:
  `tests/coverage.spec.ts` が高負荷環境下でも常に安定して 100% 合格するようになった。

### Finding 5: `web/main.ts` からのキーボードショートカット制御の分離

- **背景**:
  `web/main.ts` は 1,040 行を超える巨大ファイルとなっており、UI初期化、キーボードショートカット、URLクエリパラメータ、ファイル入出力など多岐にわたる責務が混在していた。
  特にキーボードイベント処理（18面回転、Space再生/停止、Arrow前進/後退/タブ移動、Home/End、Esc/Help等）は独立した純粋な入力ディスパッチャとして分離可能であった。
- **対処**:
  1. `web/keyboard-shortcuts.ts` を新設。
     - `setupKeyboardShortcuts(actions, getContext)` 関数を定義。
     - `KeyboardActions` インターフェースにより、メインスレッド・ストア・UIコンポーネントとの疎結合化を実現。
     - `document.addEventListener("keydown", handler)`、フォーカス外れ時の `blur` イベント、タブ非表示時の `visibilitychange` イベントを集約。
     - テキスト入力中（`INPUT` / `TEXTAREA`）のイベント無視や、修飾キー（Meta/Ctrl/Alt）押下時のブラウザデフォルト挙動維持、モーダルオープン時の無効化などを網羅。
  2. `web/main.ts` では `setupKeyboardShortcuts` を呼び出してアクション群（面回転、ステップ再生、タブ切替等）をマッピングする形へリファクタリング。
  3. `tests/coverage.spec.ts` の `page.evaluate` ユニットテストブロックに、`keyboard-shortcuts.ts` の全キー分岐、イベントリスナー解除、フォーカス判定などを網羅するテストケースを追加。
- **結果**:
  - `web/keyboard-shortcuts.ts`: 行カバレッジ **95.0%〜100.0%** を達成。
  - `web/main.ts`: 行カバレッジ **78.55%**（要求閾値 65% を余裕でクリア）。
  - 入力制御の責務が単一ファイルに集約され、保守性と可読性が大幅に向上。

### Finding 6: Playwright 設定におけるアーティファクト出力ディレクトリの明示

- **背景**:
  テスト実行時のトレースやスクリーンショット等の出力先が設定ファイル上で明示されておらず、並行テスト実行や CI 環境での競合リスクが存在した。
- **対処**:

- **結果**:
