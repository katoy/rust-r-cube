# 3x3 ルービックキューブ・ソルバー評価と改善提案書

本ドキュメントでは、本プロジェクトにおけるルービックキューブ（およびスーパーキューブ）の解決ソルバーについて、現在の設計・実装の適切性を評価し、さらなる最適化と発展のための具体的な改善案をまとめます。

---

## 1. 現在の実装の適切性（優れている点）

現在のソルバーは、Webアプリ（WASM）およびデスクトップでの実用性を重視した、非常にバランスの良い優れた設計になっています。

* **探索空間の適切な分離（ヒューリスティックなセンター修正）**
  スーパーキューブ（センターの向きがあるキューブ）を解く際、色解決（Kociemba）の後に「色保存的（他のパーツを崩さない）」な修正公式を適用するアプローチは非常に強力です。これにより、探索空間が $2,048$ 倍に爆発するのを防ぎ、ミリ秒単位での安定した解決を実現しています。
* **WASMに最適化されたチャンク設計**
  JavaScriptのシングルスレッド環境において、探索の状態を保持し、一定ステップごとに実行権をブラウザに返却する `SolverState::process_chunk` の実装は、Web UIのフリーズを防ぐためのベストプラクティスです。
* **初期回転軸の並列多様性（Rayon）**
  キューブ全体をあらかじめ回転させた4つの状態で並行探索する設計は、単にマルチコアを活かすだけでなく、Kociembaアルゴリズムの特性（最初に見つけた解を採用する）を利用して、**より手数の短い解法を早く見つけ出す確率を高める**効果があり、非常に巧妙です。

---

## 2. さらなる改善の余地（より良い実装の可能性）

将来的にこのソルバーを「よりプロ仕様」または「極限まで最適化」する場合、以下の4つの発展アプローチが考えられます。

### ① センター自転の Phase 2 統合（真の最短手数へのアプローチ）
* **現状**: 
  色解決後にセンターを修正するため、全体の解決手順が「Kociembaの手順（約20手）」＋「センター修正手順（最大で数十手）」となり、スーパーキューブとしての合計手数が長くなりがちです。
* **より良い実装**: 
  Kociembaの Phase 2 探索の時点で、センターの自転状態を表す座標（Center Orientation Coordinate: $4^6 \div 2 = 2,048$状態）を探索状態に組み込みます。Phase 2 の探索空間に $2,048$ を掛けても約 $4 \times 10^{13}$ 程度であり、枝刈りテーブルを適切に設計すれば、「色とセンターの向きを同時に、最短手順で解決する解」を直接探索できます。

### ② 群の対称性（Symmetry）の利用によるメモリとバイナリサイズの削減
* **現状**: 
  枝刈りテーブル（Pruning Tables）の生成に約 4MB のメモリを使用しています。デスクトップでは問題ありませんが、WASMのロード時間としては軽量化の余地があります。
* **より良い実装**: 
  ルービックキューブ群の持つ $48$ 個の対称性（回転や鏡映）を利用します。対称な状態を同一の「同値類」として扱うことで、テーブルサイズを **約 1/16〜1/48 に圧縮** できます（Kociemba氏のオリジナル論文でも実装されている手法です）。これにより、WASMのファイルサイズを劇的に小さくできます。

### ③ 枝刈りテーブルの事前コンパイルまたはバイナリ埋め込み
* **現状**: 
  アプリの初回起動時（または初回解決時）に、メモリ上で枝刈りテーブルを数秒かけて生成しています。
* **より良い実装**: 
  Rust の `build.rs`（ビルドスクリプト）を利用して、コンパイル時にテーブルを計算してファイルに書き出し、コンパイル時に `include_bytes!` マクロでバイナリに直接埋め込みます。これにより、起動時の初期ロード時間および解決開始時のタイムラグを完全に **ゼロ（0ms）** にできます。

### ④ スレッド間キャンセルのレスポンス向上 (`AtomicBool`)
* **現状**: 
  Rayonによる並列探索において、いずれかのスレッドが解見発見時に他スレッドを中断する処理が、探索ステップの深さの境界付近でのみ行われている可能性があります。
* **より良い実装**: 
  `Arc<AtomicBool>` による `aborted` フラグを `Search` 構造体のアクティブな探索ループ（特に対帰納的探索のノード展開箇所）の内部に渡し、より高い頻度でチェックさせます。これにより、解発見時の他スレッドの即時中断（Early Abort）のレスポンスがミリ秒単位になり、CPUリソースの解放が速くなります。
